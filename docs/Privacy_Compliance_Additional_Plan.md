## 2. 구현 계획

### P0 — 기존 P0와 함께 먼저 끝낼 항목

#### A1. 마이그레이션 체계 (h의 해결, 다른 모든 항목의 전제)
1. `schema_migration(version, applied_at)` 테이블과 번호가 붙은 SQL 파일(`migrations/0001_*.sql`)을 둔다. 앱 시작 시에는 적용만 하고 트랜잭션 하나에 한 버전씩 실행한다.
2. 현재 `db.ts`의 DDL을 `0001`로 옮기고, 기존 DB는 "이미 적용됨"으로 표시한다.
3. 개인정보 관련 열 추가는 모두 이 경로로만 한다.

완료 조건: 빈 DB와 기존 DB 양쪽에서 같은 최종 스키마가 되고, 두 번 실행해도 변화가 없다.

#### A2. 개인정보 데이터 목록과 자동 검사 (코드 하나로 모든 항목을 묶는 안전망)
1. `docs/Privacy_Data_Inventory.md`에 열·객체마다 `분류(직접식별/가명/통계/비개인) · 목적 · 근거(동의 C1~C3/계약/법령) · 보유기간 · 삭제 경로 · 외부 전송`을 적는다.
2. 테스트가 DB 열 목록을 읽어 목록에 없는 열이 있으면 실패한다. 새 열을 추가한 사람이 분류를 같이 적게 만든다.
3. 이 표가 처리방침 보유기간 표와 §3.3 배치 설정의 단일 출처가 된다.

완료 조건: 열 하나를 분류 없이 추가하면 CI가 실패한다.

#### A3. 상대 선수 식별자 제거 (a) — 결정: 저장하지 않는다
1. 워커의 `parseAnalysis`와 타임라인 생성에서 **상대 handle을 출력하지 않는다**. 내 플레이어 식별(상태 문서 §4)이 필요해지면 내 handle만 저장한다.
2. 이미 저장된 행은 A1 마이그레이션으로 `analysis`의 상대 handle을 비우고, 타임라인 객체는 §3.1 파생 데이터 전환 때 다시 만든다. 그 전까지는 소유자 경로 응답에서도 상대 handle을 지우는 방어 처리를 둔다.
3. 리플레이 원본의 채팅·상대 이름은 §3.1 원본 파기가 끝나야 사라진다. 처리방침에 그 기간을 정확히 쓴다.

완료 조건: 업로드 → 분석 뒤 DB·R2의 어떤 객체에도 상대 handle 원문이 없다는 자동 검사가 통과한다.

#### A4. 신고·문의의 보유기간과 필드 축소 (b, f)
1. `user_agent`는 브라우저 계열·주 버전 정도로 줄여 저장한다(300자 원문 저장을 중단). 문의 처리에 필요 없으면 아예 저장하지 않는다.
2. 상태 `RESOLVED`·`DISMISSED`인 신고·문의에 만료일을 두고 §3.3 배치로 본문·첨부·`user_agent`·`page`를 지운다. 운영자가 되돌릴 일이 없는 최소 보존만 남긴다.
3. 계정 삭제 시 보존하는 `kind='replay'` 신고에서 `user_agent`·`page`·`body` 중 계정 연결이 가능한 값을 같이 비운다(`reason`·결과만 유지).
4. 운영자 웹훅에는 제목 대신 `kind`와 번호만 보낸다. 제목을 보내려면 위탁 목록과 처리방침에 올린 뒤로 한정한다.

### P1 — 접근 통제와 사고 대응

#### A5. 운영자 접근 통제와 접근 기록 (c, k)
1. 공유 `ADMIN_TOKEN`을 운영자별 계정(또는 최소한 이름이 붙은 토큰 여러 개)으로 바꾸고 폐기할 수 있게 한다.
2. `admin_audit(actor, action, target_type, target_id, at)`에 신고 열람·스크린샷 열람·상태 변경·리플레이 숨김 해제를 남긴다. 본문은 기록하지 않는다.
3. 스크린샷은 서명된 단기 URL 또는 서버 경유로만 열고 열람마다 기록한다.
4. 접근 기록 보관기간과 정기 점검 방법을 A2 표에 넣는다.

#### A6. 세션 무효화와 키 분리 (d)
1. `app_user.session_version`을 두고 세션 쿠키에 버전을 넣는다. 로그아웃(전체), 회원 탈퇴, 동의 철회 이후 보안 이벤트에서 값을 올려 모든 세션을 끊는다.
2. 키를 용도별로 파생한다: `HKDF(SESSION_SECRET, "session")`, `"ip-rate"`, `"reporter"`. §3.4의 기간 키와 한 번에 구현한다.
3. 키 회전 절차를 문서화한다(회전 시 영향: 전원 재로그인, 신고 횟수 제한 초기화).

#### A7. 로그 위생 (e)
1. `errorResponse`와 외부 연동 오류 로깅을 한 래퍼로 모으고, 요청 본문·쿼리·헤더는 남기지 않는다. 오류 코드와 요청 ID만 남긴다.
2. 앱이 IP를 로그에 쓰지 않는지 테스트하고, 호스팅(Railway) 로그의 IP·보관기간은 운영 설정으로 확인해 A2 표에 적는다.
3. 로그 검사 테스트: 알려진 PII 패턴(handle 형식, 이메일, IP)을 넣은 요청의 오류 로그에 값이 나타나지 않는다.

#### A8. 유출 사고 대응 (k)
1. 운영 문서 `docs/Incident_Response.md`: 탐지 신호(비정상 export 건수, 관리자 열람 급증), 판단 기준, 통지 대상·시한·내용, 담당자.
2. 영향 범위를 뽑는 읽기 전용 쿼리를 미리 둔다(사용자별 보유 항목: A2 표 기반).
3. 연 1회 모의 훈련 일정을 기록한다.

### P2 — 권리 행사 보강과 운영 정합성

#### A9. 백업 보관과 삭제 전파 (g)
1. DB·R2 백업의 **최대 보관기간**을 정한다. 처리방침의 "삭제 즉시"를 "백업은 N일 안에 순환 삭제"로 쓴다.
2. 삭제 원장 `deletion_ledger(kind, subject_hash, done_at)`을 둔다. 개인정보 없이 "이 사용자/리플레이는 삭제됨"만 기록하고, 백업 복원 직후 반드시 원장을 다시 적용하는 복구 절차와 스크립트를 만든다.
3. 복원 리허설에서 삭제된 계정이 되살아나지 않는 것을 확인한다.

#### A10. 열람·정정·처리정지 창구 (j, i) — 결정: 동의 해제가 처리정지
1. 처리정지는 별도 스위치 없이 **동의 해제로 자동 접수**한다. C1 해제 = 새 업로드 거부와 분석 중단, C2 해제 = 공개·통계 제외, C3 해제 = 학습 후보 제외. 해제 화면에 각각 무엇이 멈추는지 한 줄씩 표시하고, `consent_log`에 시각을 남겨 처리 기록으로 쓴다.
2. 해제가 즉시 반영되는지 종단 테스트(C2 해제 직후 공개 목록·상세·통계에서 사라짐)를 추가한다.
3. `exportAccount`의 항목을 A2 표와 대조해 보유 항목 전부를 포함하거나 제외 사유를 문서에 둔다(`evaluation`, 신고 부가정보 등). 자동 대조 테스트를 추가한다.
4. 정정·기타 요청은 문의 종류 `privacy_request`를 추가하고 접수·처리 시각을 남긴다.

#### A11. 신고자 결과 통지 (b 연장)
신고자가 연락처를 남기지 않는 설계(HMAC만 저장)와 "처리 결과 통지"는 충돌한다. 로그인 사용자 신고에 한해 내 신고 목록의 상태 표시만 제공하고, 연락처 수집은 하지 않는다. 비로그인 신고는 통지하지 않는다고 처리방침에 쓴다.

#### A12. 업로더 점검 (l)
1. 업로더 로그·원장에 남는 경로를 파일 이름만으로 줄이거나 해시로 바꾼다.
2. 로그 보관 크기·기간과 삭제 메뉴(연결 해제 시 로컬 데이터 삭제 선택)를 둔다.
3. 업로더가 서버로 보내는 모든 필드(`client_version`, 기기 레이블)를 A2 표에 올린다.

#### A13. 리플레이별 공개·학습 제외 (신규, 코드에서 확인된 결함 포함)
확인된 문제: `setConsent`가 동의를 바꿀 때마다 사용자의 **모든** 리플레이의 `c2_at_upload`·`c3_at_upload`를 현재 동의 값으로 덮어쓴다(`consent.ts:38`). 따라서 (1) 업로드 시점 스냅샷이 아니고 §3.8의 `c3_consent_at_upload` 전제와 충돌하며, (2) C2를 껐다가 다시 켜면 **비공개로 두고 싶던 과거 리플레이까지 전부 다시 공개**된다. 리플레이 개별 삭제는 있으나 "분석은 유지하고 공개만 제외"하는 수단이 없다.

구현:
1. `user_replay`에 리플레이별 설정 `visibility_override`(`default` | `private`)와 `training_excluded boolean`을 추가한다(A1). 공개 조건은 `c2_at_upload and visibility_override <> 'private'`로 바꾼다(`PUBLIC_WHERE`와 통계 쿼리 모두).
2. 동의 변경 시 일괄 덮어쓰기를 정한 규칙으로 바꾼다: **철회는 전체에 즉시 적용**, **재동의는 과거 리플레이에 소급하지 않고 새 업로드부터**, 과거 리플레이의 재공개는 사용자가 리플레이별로 직접 켠다(또는 "과거 리플레이도 공개" 확인 단계를 별도로 둔다). `*_at_upload`는 업로드 시점 값으로 되돌린다.
3. 내 리플레이 상세·목록에 "공개하지 않음" 토글과 "AI 학습에서 제외" 토글을 둔다. 켜는 즉시 공개 목록·공유 링크·타임라인·통계(`bumpStats`)에서 빠지고, 이미 받은 공유 링크는 404가 된다.
4. 프로게이머 연습처럼 노출되면 안 되는 경기를 위해 **업로드 전 제외**도 둔다: 업로더에서 "이번 경기는 올리지 않음/비공개로만 올림" 선택(A12와 같은 변경). 서버는 `visibility_override`를 업로드 요청으로도 받는다.
5. 기본값은 계정 동의를 따르고, 개별 설정은 항상 더 보수적인 쪽이 이긴다.

완료 조건: C2를 껐다 켜도 비공개로 지정한 리플레이는 공개되지 않는다. 비공개 지정 직후 공개 상세·공유 링크·타임라인이 모두 404이고 통계에서 제외된다.

#### A15. 이벤트·대회 리플레이 보관과 공개 결정 (신규)
요구: 이벤트·대회 경기는 바로 공개하면 안 되고 운영자가 공개를 결정해야 하며, 그 동안 리플레이 원본 자체를 보관해야 한다. 기존 계획 §3.1("분석 뒤 원본 삭제")과 충돌하므로 **원본 삭제의 예외 범주**로 명시한다.

현재 코드의 위치:
- **AI 대 AI 이벤트(콜로세움)**: 이미 `replay` 테이블에 원본을 두고 `publish_at`이 미래면 목록·상세·다운로드 모두 404다(`Colosseum_Ingest.md`). 운영자가 올리는 경기이고 개인정보가 없으므로 §3.1 삭제 대상이 **아니다**. 이 경로는 그대로 둔다. 단, 공개 결정을 시각 예약만이 아니라 "보류 → 공개" 수동 전환으로도 할 수 있는지 확인한다(`publish_at`을 먼 미래로 두는 방식이 지금의 보류 수단이다).
- **사람 참가자의 경기(사용자 업로드)**: `user_replay`에 들어가며 §3.1이 그대로 적용된다. 아래 설계가 필요하다.

설계 (사람 참가자 이벤트):
1. `user_replay`에 `retention_class`(`standard` | `event_hold`)와 `event_id`, `hold_until`을 추가한다(A1 마이그레이션).
2. **이벤트별 별도 동의**를 받는다. C1~C3와 독립이고, 이벤트 참가 신청 화면에서 "이 대회 경기의 원본 리플레이를 운영자가 보관하고, 공개 시점은 운영자가 정한다. 보관 기간은 대회 종료 후 N개월"을 보여 주고 확인받는다. 동의 기록은 `consent_log`처럼 이벤트·버전·시각을 남긴다.
3. 업로더는 참가 중인 이벤트 경기만 `event=<slug>`로 올린다(선택이 아니라 이벤트 모드 스위치). 서버는 동의가 없는 사용자의 `event` 업로드를 거절한다.
4. `event_hold` 리플레이는 §3.1 원본 삭제와 §3.3 보관 만료에서 `hold_until`까지 제외한다. `hold_until`이 지나면 일반 규칙으로 돌아간다.
5. **공개는 운영자 결정만으로** 한다(`published_by_operator_at`). 참가자의 C2나 리플레이별 공개 스위치로는 공개되지 않고, 운영자가 공개하기 전까지 공개 목록·통계·공유 링크에서 모두 404다. 참가자 본인은 자기 경기를 볼 수 있다.
6. 원본에 접근하는 운영자 동작(다운로드·공개·삭제)은 A5 접근 기록에 남긴다. 이벤트 원본은 서명된 단기 URL로만 연다.
7. 철회: 참가자가 이벤트 동의를 철회하면 이후 업로드는 막고, 이미 낸 경기는 대회 판정·분쟁 대응에 필요한 동안(`hold_until`까지) 보관한다는 점을 동의 문구에 적는다. 그 뒤 삭제한다.
8. 상대 handle(A3): 두 선수 모두 같은 이벤트 참가자이므로 이벤트 경기에 한해 참가 등록 ID로 연결하고, 원 Battle.net handle은 저장하지 않는다.

**프로게이머 리그를 염두에 둔 추가 설계** (확정: 사람 참가자의 자동 업로드 포함, 리그가 주 용도)
9. **자동 업로드의 범위 한정**: 이벤트 모드는 항상 켜 두는 스위치가 아니라 **경기 일정 창(시작~종료 시각)** 안의 경기만 올린다. 일정 창이 끝나면 자동으로 일반 모드로 돌아간다. 리그 경기와 평소 연습 경기가 섞여 올라가지 않게 하는 것이 핵심이다. 로비에서 이벤트 경기를 식별하는 표식(상태 문서 §4 "로비 설정 식별 미구현")이 생기면 그 표식과 일정 창을 함께 조건으로 건다. 그 전에는 일정 창 + 참가자 등록 ID 일치로 판정한다.
10. **공개 표기 동의를 따로 받는다**: 일반 공개 리플레이는 익명(핸들·이름 제거)이지만, 리그는 선수 이름·소속·방송 닉네임을 공개하는 것이 보통이다. 이벤트 동의에 `표기 방식`(실명/활동명/익명)을 항목으로 두고, 이 값은 이벤트 공개 페이지에서만 쓰며 일반 공개 경로(`publicReplays`)에는 영향을 주지 않는다. 미성년자는 만 14세 이상 확인에 더해 법정대리인 동의가 필요한지 운영자가 리그 규정과 함께 확인한다.
11. **공개 전 보호(스포일러·방송 지연)**: 공개 시각은 경기 종료가 아니라 "방송·판정 완료 후"로 운영자가 정한다. 공개 전에는 참가자 본인에게도 상대 시점의 정보가 새지 않도록, 참가자가 보는 분석에서 상대의 비공개 정보(예: 상대 시점 빌드)는 공개 시각 전까지 숨기는 옵션을 둔다. 라이브 경기 중에는 분석 결과를 내지 않는다(경기 종료 후 업로드이므로 기본 충족).
12. **분쟁·부정행위 검토용 보관**: 리그는 판정 분쟁, 상금, 부정행위 조사가 있어 보관 기간이 일반 이벤트보다 길 수 있다. `hold_until`은 이벤트마다 정하고(제안: 시즌 종료 후 1년, 분쟁 접수 시 해결까지 연장), 연장 사유와 승인자를 기록한다. 상금·세무 자료는 리플레이와 분리해 별도 법정 보관 기준을 따른다(Challenge S1 정책에서 결정).
13. **운영자 권한 분리**: 리그에는 심판·방송 담당 등 여러 사람이 필요해진다. 지금의 "운영자 한 명" 전제(A5의 이름 붙은 토큰)를 넘어 **역할별 권한**(원본 열람 가능 / 공개 결정 가능 / 메타데이터만)과 접근 기록을 이 시점에 필수로 한다. 원본 열람 권한은 최소 인원에게만 준다.
14. **참가자 열람권**: 본인 경기의 원본·분석을 대회 후에도 내려받을 수 있게 할지(현재 사용자 업로드는 원본 다운로드 경로가 없다)를 리그 규정으로 정한다. 정하기 전까지는 원본을 내려받는 경로를 만들지 않는다.

완료 조건: 동의 없는 사용자의 `event` 업로드가 거절된다. `event_hold` 리플레이가 평가·분석 완료 뒤에도 `hold_until`까지 삭제되지 않고, 운영자가 공개하기 전에는 어떤 공개 경로에도 나오지 않는다. `hold_until` 이후에는 배치가 삭제한다.

## 4. 결정 사항과 남은 확인 (2026-10-28 반영)

**결정됨**
- 운영자는 한 명이다. A5는 계정 체계 대신 **이름이 붙은 토큰 여러 개(폐기 가능) + 접근 기록**으로 줄인다. 토큰은 정기 교체하고 운영자 한 명이 쓰는 기기를 목록에 적는다.
- 개인정보·고충 처리 연락처는 서비스 전용 메일 `sc2.bpm@gmail.com`(2단계 인증 완료)이고, 운영자 표기는 "BPM 리플레이 서비스 운영팀"을 기본으로 한다. 운영 환경 `PRIVACY_CONTACT`·`PRIVACY_OPERATOR_NAME`에 같은 값을 넣는다. 메일로 온 요청은 `privacy_request` 문의로 옮겨 접수·처리 시각을 기록한다(A10).
- 상대 handle은 저장하지 않는다(A3).
- 처리정지는 동의 해제로 자동 접수한다(A10). 리플레이별 삭제·비공개는 A13에서 추가한다.

**보유기간 제안 (1~2년 범위, 운영자 확정 필요)** — A2 표와 §3.3 배치의 기본값으로 쓴다.

| 데이터 | 제안 | 비고 |
|---|---|---|
| 분석 성공 리플레이 원본 | 평가 직후 삭제 (§3.1) | 최장 7일. 이벤트 보류(`event_hold`)는 예외로 대회 종료 후 N개월(A15) |
| 실패·미지원 원본 | 30일 | 재분석용 |
| 분석 결과·타임라인 | 사용자가 삭제할 때까지 | C1 동의 유지 중 |
| 해결·기각된 신고·문의 | 1년 | 분쟁 대응 상한 |
| 신고자 횟수 제한 해시 | 24시간 | 1~2년이 아니라 짧게. 장기 보관할 이유가 없다 |
| 운영자 접근 기록 | 1년 | 사고 조사용 |

| DB·R2 백업 | 30일 순환 | A9 |
| 장기 미접속 계정 | 2년 뒤 안내 후 파기 | 법정 휴면 기준 해당 여부는 운영자 확인 |

**Railway 검토 (A14, 일반 지식 기준이라 운영 화면에서 확인 필요)**
1. 리전: 서비스와 Postgres를 둘 리전을 정한다. 한국 리전이 없을 수 있어 국외 이전·위탁 고지(운영자, 이전 국가, 시기·방법, 항목, 목적, 보유기간)가 필요한지 확인한다. R2의 보관 위치(관할 지정 여부)도 같은 표에 적는다.
2. Postgres 백업: 자동 백업 제공 여부, 보관일, 복원 방법은 플랜에 따라 다르다. 없으면 `pg_dump`를 R2에 암호화해 올리는 배치를 직접 만들고 A9의 30일 순환을 맞춘다.
3. 로그: 보관일과 접근 권한을 확인한다. 앱이 IP를 남기지 않아도 플랫폼 요청 로그에는 남을 수 있다(A7).
4. 비밀값: `SESSION_SECRET`, `ADMIN_TOKEN`, R2 키, DB URL을 프로젝트 변수로만 두고 팀 접근 목록을 운영자 한 명으로 제한한다. 2단계 인증을 켠다.
5. Postgres 공개 접근(TCP 프록시)을 끄고 내부 네트워크로만 연결한다. 워커 서비스도 같은 환경에서 내부 주소로 호출한다.
6. 처리방침의 위탁 목록(Railway, Cloudflare R2, Blizzard OAuth, 선택적 Discord/Slack 웹훅)을 이 검토 결과와 일치시킨다.

**남은 확인**: 위 보유기간 값 확정, 동의 이력·휴면의 법정 기간, 웹훅 사용 여부(쓰지 않으면 A4 4항은 삭제만 하면 된다).

## 6. 처리방침을 바꿀 때의 절차 (§3.6)

1. `lib/policyVersions.ts`의 `POLICY_CHANGELOG` **맨 끝에** 항목을 추가한다. `version`은 새 날짜 문자열, 한/영 요약(`ko`, `en`)은 사용자에게 그대로 보이는 한 줄이다.
2. **고지 변경**(연락처, 오탈자, 더 쉬운 설명): `kind: "notice"`. 모든 로그인 사용자에게 배너로만 알린다. 아무것도 멈추지 않는다.
3. **동의 변경**(처리 목적, 항목, 보유기간이 이전 동의가 설명하지 않은 방식으로 바뀜): `kind: "consent"`와 `affects: ["c2", "c3"]`처럼 영향받는 동의만 적는다. 배포 후 사용자가 처음 동의를 읽는 순간 그 동의가 꺼지고 다시 확인을 받는다. 영향이 없는 동의는 그대로다. 법적으로 재동의가 필요한지의 판단은 운영자가 한다. 확신이 서지 않으면 재동의 쪽으로 기울인다(켜 둔 채로 바뀐 처리를 돌리는 것이 더 위험하다).
4. 같은 변경에서 처리방침 페이지, 동의 화면 문구(`ConsentToggles`), 업로더 설정 문구, `Privacy_Data_Inventory.md`를 함께 고친다.
5. 배포 전에 `npm run test:privacy`와 `lib/policyVersions.test.ts`를 돌리고, 가능하면 `onboarding-flow-test.mjs --phase before/after`로 확인한다(`BPM_POLICY_CHANGELOG_JSON`으로 이력을 바꿔 시험).
