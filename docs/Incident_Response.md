# 개인정보 유출 사고 대응 절차

**기준일:** 2026-10-28
**대상:** BPM 사이트·워커·저장소(Railway, Cloudflare R2). 운영자 연락처 `sc2.bpm@gmail.com`.

법률 자문이 아니다. 통지·신고의 대상, 기한, 내용은 사고 당시 현행 개인정보 보호법과 정보통신망법을 운영자가 확인해서 따른다. 아래 기한 숫자는 작성자의 기억에 바탕한 것이라 **확인 전에는 확정으로 쓰지 않는다.** 각 단계는 사고가 의심되는 즉시 시작하고, 확신이 설 때까지 기다리지 않는다.

## 1. 사고의 정의

다음 중 하나라도 일어났거나 일어났을 가능성이 있으면 사고로 다룬다.

- 데이터베이스, 객체 저장소, 백업의 내용을 권한 없는 사람이 읽거나 내려받았다.
- 비밀값(`SESSION_SECRET`, `BPM_HANDLE_KEY`, 운영자 토큰, `WORKER_TOKEN`, 저장소 키, DB 비밀번호)이 노출되었다.
- 사용자 A의 데이터가 사용자 B나 비로그인 사용자에게 보였다(공개 페이지의 비공개 리플레이 노출 포함).
- 운영자 계정이나 토큰이 도용되었다.
- 삭제·비공개로 약속한 데이터가 그대로 남아 접근 가능했다.

## 2. 탐지 신호 (지금 확인할 수 있는 것)

| 신호 | 어디서 | 의미 |
|---|---|---|
| 운영자 작업 기록의 낯선 시각·행동 | `GET /api/admin/audit` (owner) | 토큰 도용, 대량 스크린샷 열람 |
| `denied` 기록, 알 수 없는 토큰 경고 | 감사 기록, 서버 로그 | 토큰 추측, 잘못된 역할 사용 |
| 원본 삭제 실패·포기 | `run-retention.mjs` 종료 코드 1, 보고서 `gaveUp` | 저장소 접근 문제 |
| 비정상적인 내보내기·삭제 요청 급증 | 서버 로그, DB | 계정 탈취 |
| 사용자·공개 페이지 신고(비공개인데 보임) | 문의함, 개인정보 메일 | 노출 |
| Railway·R2·GitHub·Battle.net의 보안 알림 | 해당 서비스 알림 메일 | 외부 원인 |

## 3. 처음 한 시간

1. **기록 시작.** 시각, 발견 경위, 확인한 사실을 `docs/incidents/<날짜>-<짧은 이름>.md`(저장소 밖 비공개 문서여도 된다)에 시간순으로 적는다. 추측과 사실을 구분한다.
2. **증거 보존.** 로그를 지우지 않는다. 서버 로그·감사 기록·DB 상태를 사본으로 저장한다. 보관기간 배치(`run-retention.mjs --delete`)를 사고 조사가 끝날 때까지 멈춘다.
3. **차단.** 원인에 맞는 것만 한다(아래 4).
4. **범위 파악.** 5의 쿼리로 영향받은 사용자와 항목을 센다.

## 4. 차단 조치와 그 영향

| 노출된 것 | 조치 | 영향 |
|---|---|---|
| `SESSION_SECRET` | 새 값으로 교체하고 배포 | 모든 사용자가 다시 로그인한다. 신고 횟수 제한이 초기화된다. 다른 데이터는 그대로 |
| 운영자 토큰 | `ADMIN_TOKENS`에서 해당 항목을 지우고 새 토큰으로 교체, 배포 | 해당 운영자만 영향. 감사 기록으로 그 토큰이 한 일을 확인 |
| `WORKER_TOKEN` | 서버와 워커의 값을 함께 교체 | 워커가 잠시 멈춘다 |
| `BPM_HANDLE_KEY` | **유출이 확정된 경우에만** 교체한다. 교체하면 같은 경기를 두 선수가 올린 것을 새 분석과 옛 분석이 알아보지 못한다. 유출되면 핸들 해시를 추측해 볼 수 있으므로 영향 범위에 선수 핸들을 포함해 판단 | 통계의 같은 경기 중복 제거가 일부 깨진다 |
| 저장소 키(R2), DB 비밀번호 | 서비스에서 새 키를 만들고 교체, 옛 키 폐기 | 교체 순간 짧은 중단 |
| 한 사용자 계정 | 그 계정으로 "모든 브라우저에서 로그아웃"을 대신 실행(세션 버전 증가), 런처 연결 해제 | 그 사용자만 |
| 공개 노출(비공개인데 보임) | 해당 리플레이를 즉시 비공개로 지정하거나 삭제, 원인 코드 수정 전까지 공개 페이지 차단 | 해당 리플레이 |

## 5. 범위 파악 쿼리 (읽기 전용, 운영 DB에서 실행)

항목별 보유 데이터는 `docs/Privacy_Data_Inventory.md`가 기준이다. 사고가 영향을 준 종류만 센다.

```sql
-- 영향 시간대에 계정이 만들어졌거나 활동한 사용자 수
select count(*) from app_user where created_at between :from and :to;

-- 특정 사용자가 보유한 데이터의 종류와 양
select (select count(*) from user_replay where user_id = :uid) as replays,
       (select count(*) from user_replay where user_id = :uid and source_deleted_at is null) as originals_still_kept,
       (select count(*) from feedback where user_id = :uid) as messages,
       (select count(*) from device_token where user_id = :uid and revoked_at is null) as launchers;

-- 아직 원본 파일이 남아 있는 리플레이(닉네임·핸들·채팅 포함 가능)
select count(*) from user_replay where source_deleted_at is null and status <> 'QUEUED';

-- 공개 상태인 리플레이
select count(*) from user_replay where c2_at_upload and visibility_override <> 'private' and hidden_at is null and status = 'READY';

-- 운영자 접근 기록
select actor, action, target, at from admin_audit where at between :from and :to order by at;
```

영향이 "닉네임·핸들·채팅이 든 원본"인지, "해시·분석 파생 데이터"인지를 먼저 가른다. 파생 데이터에는 핸들 원문과 닉네임이 없다(A3).

## 6. 통지와 신고

1. **판단:** 노출된 정보가 개인정보인지, 몇 명인지, 어떤 항목인지, 악용 가능한지를 기록한다.
2. **정보주체 통지:** 영향을 받은 사용자에게 지체 없이 알린다. 법이 정한 기한과 내용(유출 항목, 시점과 경위, 이용자가 할 수 있는 조치, 대응 조치와 피해 구제 절차, 담당 부서와 연락처)을 현행 조문에서 확인해 따른다. 작성자의 기억으로는 알게 된 때부터 72시간 안이지만 확정이 아니다.
3. **감독기관 신고:** 규모(작성자의 기억으로는 1천 명 이상 등)나 민감 정보 여부에 따라 개인정보보호위원회 또는 한국인터넷진흥원에 신고하는 의무가 있을 수 있다. 해당 여부를 운영자가 확인한다.
4. **알릴 수단:** 가입 시 받은 정보는 Battle.net 계정 식별자와 표시 이름뿐이고 사용자의 이메일은 없다. 따라서 사이트 공지(로그인 후 배너), 런처 알림, 공개 공지 페이지가 주된 수단이 된다. 이 한계를 평시에 알고 있어야 하며, 이메일 수집 여부는 별도로 결정한다.

### 통지문 틀

한국어: "[BPM 리플레이 서비스] 개인정보 유출 안내. 발생 시점: ○○. 유출된 항목: ○○. 경위: ○○. 이용자가 할 수 있는 조치: ○○(예: 로그아웃 후 재로그인, Battle.net 비밀번호 변경). 저희가 한 조치: ○○. 문의: sc2.bpm@gmail.com (BPM 리플레이 서비스 운영팀)."

English: "[BPM Replay Service] Notice of a personal data incident. When: …. What was affected: …. How it happened: …. What you can do: …. What we have done: …. Contact: sc2.bpm@gmail.com (BPM Replay Service Operations Team)."

## 7. 사고 후

1. 원인과 재발 방지를 기록에 적고, 코드·설정·절차 중 무엇을 바꿨는지 남긴다.
2. 이 절차에서 맞지 않았던 부분을 고친다.
3. 사고가 데이터 목록의 분류나 보유기간 가정을 바꾸면 `Privacy_Data_Inventory.md`와 처리방침을 같이 고친다.
4. 처리방침이 약속한 내용과 달랐다면(예: 삭제 약속) 정정 안내를 낸다.

## 8. 평시 점검

- **연 1회 모의 훈련:** 가상의 시나리오(운영자 토큰 유출, 비공개 리플레이 노출)로 위 절차를 따라 5분 안에 범위 쿼리를 돌리고 통지문 초안을 만들어 본다. 날짜와 결과를 기록한다.
- **분기마다:** 운영자 토큰 목록을 점검하고 쓰지 않는 항목을 지운다. 감사 기록에서 낯선 행동이 없는지 본다.
- **비밀값 위치:** Railway 프로젝트 변수에만 둔다. 저장소, 채팅, 메일에 붙여 넣지 않는다.
- **운영자 변경 때:** 같은 날 그 사람의 토큰을 지우고 교체한다.
