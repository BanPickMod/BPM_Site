## 2. 요구사항 정밀화 (구현 가능한 수준으로 재정의)

기존 계획서는 "정찰해서 조합 파악 후 확장/공격/수비 결정" 같은 요구를 개념적으로만 서술했다. 구현하려면 각 항목을 측정 가능한 규칙으로 쪼개야 한다.

### 2.1 Draft AI — "유동적" 밴픽의 정의
현재 드래프트 턴에서 다음 3가지를 모두 입력으로 받아야 "유동적"이라 할 수 있다:
1. **이번 시리즈의 과거 게임 이력** (현재 이미 구현됨: `SeriesDraftState`)
2. **이번 드래프트 내에서 상대가 지금까지 밴/픽한 것** (미구현 — 가장 핵심 누락)
3. **아직 밴/픽 가능한 잔여 풀(pool)** 대비 상대적 위협도 재계산

→ 3번이 있어야 "상대가 A를 밴하면 내 추천 픽 순위가 실시간으로 바뀐다"가 성립한다.

### 2.2 Gameplay AI — APM 조절의 정의
- 난이도 등급(예: Easy/Normal/Hard/Brutal 4단계)마다 **목표 APM 범위**를 매핑하고, 실제 명령 발행 간격(틱 수)으로 환산해야 한다.
- 단순 "느리게 반응"이 아니라, **틱당 발행 가능한 명령 개수 상한 + 명령 간 최소 지연**의 조합으로 구현하는 것이 SC2 AI 스크립팅 관행과 일치한다.
- APM 수치는 "인게임 명령 이벤트 수 / 경과 분"으로 재현 가능하게 정의해, 이후 리플레이 분석으로 실측·검증 가능해야 한다(자기 검증 루프).

### 2.3 Gameplay AI — 정찰 기반 공수 판단의 정의
결정 트리를 명시적 상태 머신으로 정의:

```text
SCOUT(주기적, 예: 60초마다 1회 정찰 유닛 파견)
  → 상대 시야 확보 시 관측된 유닛 종류/수 기록 (OpponentCompositionEstimate)
  → 자신의 병력/경제 스냅샷과 비교
      army_ratio = 자신 전투력 추정치 / 상대 전투력 추정치
      eco_ratio  = 자신 자원채집 추정치 / 상대 자원채집 추정치
  → 판단 규칙(예):
      army_ratio > 1.3          → ATTACK
      army_ratio < 0.7          → DEFEND
      army_ratio in [0.7, 1.3] and eco_ratio > 1.1 → EXPAND
      정찰 정보 없음(관측 실패) → 이전 상태 유지 + 정찰 재시도
```
"전투력 추정치"는 초기에는 (유닛 수 × 고정 가중치) 같은 단순 heuristic으로 시작하고, AI-vs-AI 데이터가 쌓이면 학습 기반으로 교체한다 — 이는 `BPM_Platform_Plan.md` §1.2의 "먼저 검증 가능한 heuristic, 이후 학습 기반 확장" 원칙과 일치한다.

> **정찰 신뢰성 제약 (확정)**: `OpponentCompositionEstimate`는 실제 사람이 플레이하듯 **획득한 시야 안에서만** 채워져야 한다 — 예: 관측선/커맨드센터 스캐너로 확보한 시야에 보이는 유닛만 기록, 또는 저글링 한 마리처럼 저렴한 유닛 1기를 상대 진영에 보내 순간적으로 확인하는 방식. Galaxy의 숨겨진 변수나 트리거 상태를 직접 읽어 상대 조합을 "알고 있는" 것처럼 구현하는 것은 금지한다 (이미 `BPM_Platform_Plan.md` §10.3 "Galaxy 내부 임의 변수가 항상 노출된다고 가정하지 않는다" 원칙과 직결). 이 제약은 인게임 Commander뿐 아니라 5.1절의 대안 실행 경로(python-sc2 등)를 쓰더라도 동일하게 적용된다 — 어떤 실행 경로든 안개(fog of war)로 가려진 정보에 접근하면 안 된다.

### 2.4 밸런스 테스트베드 — 측정 지표의 정의
- **6개 조합**: TvT, PvP, ZvZ, TvP, TvZ, PvZ — 승률은 50%에 가까울수록 밸런스가 좋다고 간주 (허용 오차 범위를 명시해야 함, 예: 45~55%).
- **유닛 그룹 내 픽률 4.5:5.5**: "Pick Group"(예: Firebat ↔ Marauder) 내에서 각 유닛의 선택 비율이 45:55~55:45 범위를 벗어나면 밸런스 경보.
- **표본 크기 요건**: 위 지표를 신뢰 있게 판단하려면 조합/그룹당 최소 표본 수가 필요하다 (5절에서 통계적 신뢰구간 설계로 별도 제안).

### 2.5 BPM vs BPM_PTR — AI 연계 파이프라인의 정의
```text
패치 초안 작성 (BPM_PTR 데이터)
  → PTR 유닛/밸런스 값으로 AI-vs-AI 자동 반복 대전 N게임
  → 승률/픽률 통계가 목표 범위 내인지 자동 판정
  → 범위 밖이면 패치 보류 + 보고서 생성
  → 범위 내이면 인간 PTR 테스트 단계로 승격
  → 최종 승인 시 본 모드(BPM) 패치로 반영
```

## 3. 아키텍처 재설계

### 3.1 Draft AI — 실시간 추천 엔진
- `DraftEngine.recommend()`의 시그니처에 **현재 드래프트 상태**(`current_draft_state`: 이번 게임에서 지금까지의 양측 밴/픽 시퀀스, 남은 턴 수)를 추가.
- 점수 계산을 "매치업 고정 테이블 조회"에서 "잔여 풀 + 상대 노출 정보 기반 재랭킹"으로 변경. 학습 모델(`DraftModelTrainer`)은 유지하되, 입력 피처에 "이번 드래프트 내 상대 밴/픽"을 반영해 재훈련.
- TvT/PvP/ZvZ 동족전 후보 테이블 추가 (2.4절 6조합 요건과 맞추기 위한 선행 작업).

### 3.2 Gameplay AI — APM 스로틀러
- `BPM_AI_Commander.galaxy`에 난이도별 APM 목표를 상수로 선언하고, `Think()` 루프에서 "이번 틱에 실행 가능한 명령 예산"을 계산하는 스로틀 함수를 추가.
- 판단(무엇을 할지)과 실행(언제 명령을 내보낼지)을 분리 — 판단 로직은 아래 3.3의 상태 머신이 매 주기 결정하고, 실행은 APM 예산에 맞춰 명령을 큐잉/지연.

### 3.3 Gameplay AI — 정찰-판단 상태 머신
- 신규 모듈 `BPM_AI_Scout.galaxy`(또는 기존 Commander 확장): 정찰 타이머, `OpponentCompositionEstimate` 구조체, 2.3절 상태 머신 구현.
- 상태 전이 로그를 게임 내 디버그 채널 또는 추후 리플레이 분석이 식별 가능한 형태(예: 특정 채팅/이벤트 마커)로 남겨, Replay Analyzer가 "AI가 언제 공격/수비/확장으로 전환했는지"를 사후 검증할 수 있게 한다.

### 3.4 밸런스 테스트베드 — Self-Play 오케스트레이터 (순차 실행, 확정)
(5.1절에서 구조적 대안을 별도 제안하므로 여기서는 데이터 흐름만 정의)

**실행 방식(확정)**: 대량 병렬 실행이 아니라 **6개 조합 × 맵 풀을 순차적으로 순회**하며 표본을 누적한다. 한 번에 여러 게임을 동시에 띄우는 구조가 아니라, 한 게임씩 순서대로 실행 → 결과 기록 → 다음 조합/맵으로 이동하는 루프다. 이는 인게임 엔진(Galaxy) 기반이든 5.1절의 별도 실행 경로든 동일하게 적용되며, §5.4(CI 상시 자동화)의 배치 크기는 이 순차 처리 속도를 전제로 산정해야 한다.

```text
Orchestrator(bpm-ai-engine 신규 모듈, 예: bpm_ai/simulation/)
  → 조합 순회: [TvT, PvP, ZvZ, TvP, TvZ, PvZ] (순서 고정 또는 라운드로빈)
      → 각 조합마다 맵 풀([Solaris LE, Alcyone LE, Amphion LE, ...])을 순차 순회
          → 게임 1개 실행 → 결과(승자, 사용된 밴/픽, 진행 시간) 기록
  → StatsAggregator: 조합별 승률 / Pick Group별 픽률 계산 + 신뢰구간 (§5.3)
  → BalanceReport 생성 (목표 범위 이탈 항목 하이라이트)
```

### 3.5 모델 재학습 전략 — 점진 갱신 우선 (확정)
완전 재학습(full retrain)은 최대한 피하고, **주기적으로 신규 데이터를 정제해 기존 모델에 점진적으로 반영**하는 방식을 기본으로 한다.
- 현재 `DraftModelTrainer`는 `LogisticRegression.fit()`을 호출해 매번 전체 데이터로 완전 재학습한다. 점진 갱신을 지원하려면 `partial_fit`을 지원하는 모델(예: `SGDClassifier(loss="log_loss")`)로 교체하거나, `LogisticRegression(warm_start=True)`로 이전 파라미터에서 이어서 학습하도록 변경이 필요하다 — 이 변경 없이는 "점진적 갱신"이 구현상 불가능하므로 AI-1 작업에 포함시킨다.
- 갱신 주기는 "매 게임마다"가 아니라 **일정 주기(예: 패치 단위 또는 누적 표본 N게임 단위)로 신규 데이터를 정제(이상치/저품질 게임 제거)한 뒤 반영**한다.
- 완전 재학습은 (a) 유닛 로스터 자체가 바뀌어 피처 차원이 변하는 경우, (b) 점진 갱신 누적으로 성능이 저하된 것이 확인된 경우에만 예외적으로 수행한다.

### 3.6 데이터/모델 버전 추적
모든 시뮬레이션 게임 로그에 `ai_model_version`, `balance_patch_version` 필드를 기록해, "어떤 모델·어떤 패치 버전에서 나온 통계인지" 사후 추적 가능하게 한다 (이미 `BPM_Platform_Plan.md` §8.4에 "AI model/version 별 성과"가 언급되어 있으나 구체적 필드 요구사항은 이번에 처음 명시). 점진 갱신 방식(§3.5)에서는 이 버전 필드가 특히 중요한데, 같은 `ai_model_version`이라도 갱신 시점에 따라 실제 파라미터가 달라지므로 `model_updated_at` 타임스탬프도 함께 기록한다.

## 5. 요청 범위를 넘어서는 추가 개선 제안

이 절은 사용자가 명시적으로 요청하지 않았지만, 코드 검토 중 구조적으로 개선하면 이득이 큰 지점을 정리한 것이다.

### 5.1 "밸런스 테스트용 AI"와 "인게임 상대 AI"를 다른 실행 경로로 분리 제안
현재 계획은 두 AI(플레이어 상대용, 밸런스 테스트용)를 같은 Galaxy Commander 코드로 상정하고 있다. 그런데 밸런스 테스트베드는 **6조합 × 대량 반복 게임**이 필요해 속도와 재현성이 핵심이고, 인게임 상대 AI는 **APM 제한, 인간적인 판단 지연** 같은 "너무 빠르면 안 되는" 제약이 핵심이다. 이 둘을 하나의 코드로 유지하면 한쪽을 최적화할 때 다른 쪽이 깨진다.

**제안**: 오픈소스 `python-sc2`(BurnySc2 계열) 봇 프레임워크로 별도의 "밸런스 테스트용 자가대전 봇"을 만들어 실제 SC2 클라이언트를 헤드리스로 대량 실행하는 것을 검토한다. 이렇게 하면:
- Galaxy `BPM_AI_Commander`는 "APM 제한이 걸린 그럴듯한 상대"라는 원래 목적에만 집중할 수 있다.
- 밸런스 테스트베드는 Galaxy 트리거 제약 없이 게임을 빠르게 반복 실행하고 결과를 바로 구조화된 데이터로 받을 수 있다(리플레이 파싱 단계를 거치지 않아도 됨).
- 이미 계획서(§A.1)에서 참고 사례로 언급된 오픈소스 활용 방향과도 맞다. `python-sc2`는 스타크래프트2 커스텀 유닛/모드에도 API 레벨에서 대응 가능한지 별도 prototype 검증이 필요하다(밴픽 모드처럼 테크트리를 런타임에 바꾸는 경우의 지원 여부 확인 필요).

### 5.2 유닛 ID 정의의 단일 진실 공급원(Single Source of Truth) 부재
현재 유닛 목록/ID가 최소 4곳에 중복 정의되어 있고 서로 동기화 방법이 없다:
- `BPM_AI_Types.galaxy`의 `c_BPM_U_*` 상수
- `bpm_ai/draft/engine.py`의 `BPM_UNIT_DATABASE`
- `bpm_ai/training/dataset.py`의 `CANONICAL_UNITS`
- `BPM_Site/data/units.json` (Wiki 데이터)

유닛이 추가/개명될 때마다 4곳을 수동으로 맞춰야 하며, 이미 계획서 §4.6에서 언급한 "SC2 Data Exporter"는 Wiki용으로만 설계되어 있다. **제안**: Exporter의 출력 스키마를 확장해 Galaxy 상수 파일과 Python `BPM_UNIT_DATABASE`/`CANONICAL_UNITS`를 이 단일 JSON에서 코드 생성(codegen)하도록 만든다.

### 5.3 통계적 신뢰도 없이는 "45:55" 판정이 무의미
픽률 45:55 기준을 체크하려면 표본 크기에 따른 신뢰구간이 필요하다. 예를 들어 10게임 중 6:4 픽률은 아무 의미가 없지만 1000게임 중 6:4는 통계적으로 유의미하다. **제안**: `StatsAggregator`에 Wilson score interval(또는 단순 표준오차 기반 z-검정)을 적용해 "표본이 부족해 판단 불가" 상태를 명시적으로 표시하고, 조합/그룹별 최소 요구 표본 수를 정의한다. (계획서 §1.2에 있는 "충분하지 않은 데이터는 Not enough data로 표시" 원칙을 밸런스 통계에도 동일하게 적용하는 것.)

### 5.4 밸런스 테스트를 상시 자동화(CI 연계)
현재 계획은 밸런스 테스트를 "필요할 때 수동 실행"으로 암묵적으로 가정한다. **제안**: GitHub Actions에 주기적(예: 야간/주간) 셀프플레이 잡을 추가해 최신 패치 기준으로 N게임을 자동 실행하고, 결과를 웹 리더보드/밸런스 대시보드 데이터에 자동 반영한다. 이는 "패치할 때마다 사람이 밸런스 테스트를 챙겨야 한다"는 운영 부담을 제거하고, PTR→본모드 승격 판단(2.5절)의 근거 데이터를 항상 최신 상태로 유지한다.

### 5.5 AI 판단의 설명 가능성(Explainability) 로그
밴픽 추천과 공수 판단(2.3절)에 "왜 그렇게 판단했는지"를 구조화된 형태로 남기지 않으면, 밸런스가 깨졌을 때 원인이 "AI 판단 버그"인지 "실제 유닛 밸런스 문제"인지 구분하기 어렵다. **제안**: 각 추천/판단에 점수 구성 요소(base_score, model_score, 상태 전이 트리거 조건)를 함께 로깅해 사후 분석 가능하게 한다.

### 5.6 Python ↔ TypeScript 타입 동기화
`bpm_ai/core/manifest.py`(Pydantic)와 `types/ai.ts`(수동 작성 TS 인터페이스)가 지금은 우연히 일치하지만, 둘 다 손으로 유지되므로 시간이 지나면 드리프트가 발생한다. **제안**: FastAPI가 자동 생성하는 OpenAPI 스키마에서 TS 타입을 codegen(예: `openapi-typescript`)하도록 빌드 스크립트에 추가한다.

### 5.7 API 보안 하드닝
5.1~5.6과는 별개로, 지금 `bpm-ai-engine`의 API는 인증이 전혀 없고 CORS가 전체 허용이다. 개발 중에는 문제없지만, 대회 운영 단계(Companion/웹이 실제 통신)에서는 밴픽 결정 API에 누구나 접근/조작할 수 있다는 뜻이다. 4절 Quick Win에 최소 조치를 넣었지만, 정식 운영 전 별도 보안 검토가 필요하다는 점을 여기에 명시해둔다.

## 7. 완료 기준 (Acceptance Criteria)

- 채팅/뱅크를 통한 밴픽 Manifest 주입이 실제로 유닛별로 파싱되어 테크트리에 반영된다.
- Draft AI 추천 결과가 같은 매치업이라도 "현재 드래프트에서 상대가 무엇을 밴/픽했는지"에 따라 달라진다.
- 동일 난이도로 여러 게임을 돌렸을 때 리플레이에서 측정한 평균 APM이 해당 난이도의 목표 범위 안에 있다.
- AI가 정찰에 실패한 상황에서도 게임이 멈추거나 예외를 던지지 않고 이전 판단을 유지한다.
- 6개 종족 조합에 대해 최소 표본 수 이상의 AI-vs-AI 게임을 자동 실행하고, 승률/픽률과 신뢰구간이 포함된 리포트를 얻을 수 있다.
- 웹 AI 페이지와 밸런스 대시보드가 목업이 아닌 실제 엔진 데이터를 표시하며, 데이터가 부족한 항목은 임의 수치 대신 "Not enough data"로 표시된다.
