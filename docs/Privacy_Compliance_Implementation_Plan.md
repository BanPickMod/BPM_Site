# 개인정보 처리 준수 기능 구현 현황과 계획

**기준일:** 2026-10-28  
**기준:** 저장소의 현재 코드와 데이터 흐름  
**범위:** 사용자 리플레이, 신고·문의, 동의, 계정 삭제, 정책 변경 안내

이 문서는 개인정보 처리방침과 실제 서비스 동작을 일치시키기 위해 필요한 개발 항목의 현황과 구현 계획만 기록한다. 법률 자문이나 최종 개인정보 처리방침을 대신하지 않는다. 아직 구현되지 않은 동작은 처리방침에서 완료된 기능처럼 고지하지 않는다.

## 1. 상태 정의

| 상태 | 의미 |
|---|---|
| **구현됨** | 사용자 경로와 서버 로직이 있으며 현재 코드에서 동작을 확인할 수 있다. 운영 배포 검증은 별도다. |
| **부분 구현** | 핵심 동작 일부는 있으나 원자성, 자동화, 장애 복구 또는 사용자 흐름이 남아 있다. |
| **미구현** | 데이터 구조나 실제 실행 경로가 아직 없다. |

## 2. 현재 현황

| # | 항목 | 상태 | 현재 동작 | 남은 일 |
|---|---|---|---|---|
| 1 | 원본 리플레이 비식별화 또는 파기 | **미구현** | 분석 성공 후에도 원본 `storage_key`를 보관한다. `NOT_BPM`·`CORRUPT` 원본은 삭제하고 `UNSUPPORTED`는 재분석을 위해 보관한다. 평가 워커도 `READY` 원본을 읽을 수 있다. | 평가 입력을 비식별 파생 데이터로 전환하거나 평가 완료 뒤 원본을 삭제한다. 실패 파일에도 짧은 TTL을 적용하고 삭제 재시도를 기록한다. |
| 2 | 신고 즉시 자동 블라인드 | **부분 구현** | `opponent`·`privacy` 신고는 `hidden_at`을 설정하며 공개 목록·상세·타임라인·통계에서 즉시 제외된다. | 신고 저장과 숨김 처리를 한 DB 트랜잭션으로 묶고 동시 신고·부분 실패 테스트를 추가한다. 자동 숨김 대상 사유를 정책 문구와 일치시킨다. |
| 3 | C3 학습 후보 분리와 철회 | **미구현** | C3 동의와 변경 이력, 리플레이의 `c3_at_upload`은 존재한다. 실제 학습 후보 뷰·반출·학습 이력은 없다. | 현재 동의 상태, 업로드 시점 스냅샷, 데이터셋 반출, 학습 완료 상태를 분리하고 미학습 후보 철회를 구현한다. |
| 4 | 신고자 IP HMAC와 TTL | **부분 구현** | 원 IP 대신 `SESSION_SECRET` 기반 HMAC 값을 저장하고 최근 1시간 제출 수를 제한한다. | 기간별 키를 안정적으로 파생하고 횟수 제한 데이터를 신고 본문과 분리한다. Redis TTL 또는 `expires_at` 기반 자동 삭제를 적용한다. |
| 5 | 스크린샷 서버 측 메타데이터 제거 | **구현됨** | 서버가 PNG/JPEG/WebP를 내용으로 판별하고 EXIF·XMP·텍스트·시간 메타데이터를 제거한 결과만 비공개 저장한다. SVG와 손상 파일은 거부한다. | 운영 저장소에서 원본이 남지 않는지 종단 검증하고, 지원 형식 변경 시 제거 테스트를 함께 갱신한다. |
| 6 | 보관기간 만료 자동 파기 | **미구현** | 사용자 요청에 의한 리플레이·계정·문의 삭제는 있으나 기간 기반 스케줄러는 없다. | 리플레이, 완료된 문의·신고, 신고자 해시, 만료 인증 요청과 고립 저장소 객체의 파기 기준·배치를 구현한다. |
| 7 | 최초 로그인 온보딩 | **부분 구현** | 로그인 전 만 14세 이상 확인을 받고, C1~C3은 기본 Off이며 연령 미확인 계정의 동의 변경을 막는다. | OAuth 후 선택 동의 내용을 확인하고 모두 Off로도 완료할 수 있는 온보딩과 `onboarding_completed_at`을 추가한다. |
| 8 | 회원 탈퇴와 데이터 삭제 | **구현됨** | 원본·타임라인·분석 행, 일반 문의·첨부, 동의 기록, 기기 토큰과 계정을 삭제한다. 다른 리플레이에 대한 신고는 계정 연결을 끊고 보존한다. | 저장소와 DB 사이의 부분 실패를 재시도하는 삭제 작업/outbox를 추가하고, 보존하는 신고의 기간을 처리방침과 맞춘다. |
| 9 | 정책 버전 변경 안내·재동의 | **부분 구현** | 현재 동의와 변경 이력에 `policy_version`을 저장한다. | 사용자 버전 비교, 변경 내역 배너와 확인 흐름을 구현한다. 단순 문서 버전과 재동의가 필요한 동의 버전을 분리한다. |

## 3. 구현 계획

### P0 — 문서와 데이터 보관 약속을 맞추는 출시 차단 항목

#### 3.1 원본 리플레이 생명주기

목표 상태:

```text
UPLOADED → ANALYZING → DERIVED_READY → EVALUATING → SOURCE_DELETE_PENDING → READY
                                                    └→ 재시도 → SOURCE_DELETED
```

구현 항목:

1. 분석 결과와 비식별 타임라인에 평가에 필요한 정보가 모두 있는지 확정한다.
2. 평가 워커를 파생 데이터 입력으로 바꾸는 것을 우선한다. 불가능하면 평가 완료 직후 원본을 삭제한다.
3. `source_deleted_at`, `source_delete_attempts`, `source_delete_error` 또는 별도 삭제 작업 테이블을 추가한다.
4. `QUEUED`·`ANALYZING`·`FAILED`·`UNSUPPORTED` 상태의 원본에도 상태별 최대 보관기간을 둔다.
5. 저장소 삭제 성공을 확인한 뒤 완료 상태로 전환하고, 실패는 지수 백오프로 재시도한다.
6. 원본 삭제 후에도 내 분석·공개 재생·통계가 정상 동작하는 종단 테스트를 추가한다.

완료 조건:

- 성공한 사용자 리플레이의 원본 객체가 정해진 처리 시점 뒤 존재하지 않는다.
- 워커 실패나 서버 재시작 뒤에도 삭제 작업이 유실되지 않는다.
- 보관이 필요한 예외 상태와 최대 기간이 문서에 명시되어 있다.

#### 3.2 신고 접수와 자동 블라인드 원자화

구현 항목:

1. 공개 여부 확인, 신고 행 생성, `hidden_at` 설정을 한 트랜잭션에서 처리한다.
2. `opponent`·`privacy`만 자동 숨김할지 최종 정책과 일치시킨다.
3. 트랜잭션 완료 뒤 통계 캐시를 무효화한다.
4. 중복·동시 신고와 DB 오류를 주입한 테스트를 추가한다.

완료 조건:

- 신고가 성공했는데 리플레이가 공개로 남는 부분 성공 상태가 발생하지 않는다.
- 숨김 직후 공개 상세·공유 링크·타임라인은 404 또는 동일한 비공개 응답을 반환하고 통계에서도 제외된다.

#### 3.3 보관기간 자동 파기

구현 항목:

1. 운영자가 리플레이·문의·신고·인증 데이터별 보관기간을 먼저 확정한다.
2. 만료 대상을 조회하는 dry-run 명령과 실제 삭제 배치를 분리한다.
3. DB 행과 저장소 객체를 삭제 작업으로 연결하고 재시도·실패 알림을 둔다.
4. 만료된 디바이스 인증과 고립된 저장소 객체도 정리 대상에 포함한다.
5. 실행 건수, 실패 건수, 가장 오래된 미처리 건을 운영 지표로 남긴다.

완료 조건:

- 시간을 고정한 자동 테스트에서 각 보관기간 경계 전후의 대상이 정확히 구분된다.
- 같은 배치를 여러 번 실행해도 안전하다.
- 운영 환경에서 dry-run 결과를 검토한 뒤 실제 삭제 시험을 통과한다.

#### 3.4 신고자 횟수 제한 데이터 분리

구현 항목:

1. 기간 키를 `HMAC(masterSecret, UTC 시간 구간)`으로 파생하고 IP는 그 키로 다시 HMAC 처리한다.
2. 신고 본문에 장기 보관되는 `reporter_hash`와 단기 rate-limit 레코드를 분리한다.
3. Redis 사용 시 TTL, Postgres 사용 시 `expires_at` 인덱스와 삭제 배치를 적용한다.
4. 여러 서버 인스턴스와 재시작 상황에서 동일하게 제한되는지 시험한다.

완료 조건:

- 원 IP가 로그·DB·오류 응답에 저장되지 않는다.
- 만료된 단기 해시는 자동으로 제거된다.
- 키 회전 경계에서 과도한 차단이나 제한 무력화가 허용 범위를 벗어나지 않는다.

### P1 — 동의·계정 사용자 흐름

#### 3.5 최초 로그인 온보딩

1. OAuth 콜백 뒤 온보딩 완료 여부를 검사한다.
2. 만 14세 이상 확인과 기본 처리 안내를 표시한다.
3. C1~C3을 독립 선택으로 표시하고 모두 Off인 제출도 허용한다.
4. 완료 시 정책·동의 버전, 시각, 출처를 기록한다.
5. 미완료 계정은 업로드·기기 연결 전에 온보딩으로 이동시킨다.

#### 3.6 정책 변경 안내와 재동의

1. 개인정보 처리방침 문서 버전과 선택 동의 내용 버전을 분리한다.
2. 연락처·오탈자 같은 고지 변경은 비차단 배너로 안내한다.
3. 목적·항목·보유기간의 실질 변경은 영향받는 C1~C3만 다시 확인받는다.
4. 이전·현재 버전, 변경 요약, 확인 시각을 기록한다.

#### 3.7 삭제 신뢰성 보강

1. 회원 탈퇴 요청 시 새 업로드와 동의 변경을 먼저 차단한다.
2. 삭제할 DB 행과 저장소 객체를 작업 목록으로 고정한다.
3. 객체 삭제 후 DB 정리, 실패 재시도, 완료 확인이 가능한 상태 머신을 둔다.
4. 다른 리플레이에 대한 신고처럼 보존하는 데이터는 계정 연결 제거와 만료일을 함께 기록한다.

### P2 — 실제 AI 학습을 시작하기 전 필수 항목

#### 3.8 C3 후보·반출·학습 이력

권장 필드 또는 동등한 별도 테이블:

- `c3_consent_at_upload`: 업로드 시점 스냅샷
- `c3_eligible`: 현재 미학습 후보 자격
- `c3_dataset_id`: 반출된 데이터셋 식별자
- `c3_exported_at`: 데이터셋 반출 시각
- `c3_trained_at`: 학습 사용 확정 시각

구현 항목:

1. 학습 코드는 비식별 파생 로그의 적격 뷰만 읽게 한다.
2. C3 철회 시 `c3_trained_at is null`인 모든 후보를 즉시 제외한다.
3. 데이터셋을 생성한 뒤 학습 전 다시 동의 상태를 확인한다.
4. 데이터셋·모델 버전과 포함 근거를 감사 가능하게 기록한다.
5. 학습 기능이 없을 때는 C3가 현재 사용되지 않는다는 사실을 UI에 표시하거나 선택을 비활성화한다.

완료 조건:

- C3가 Off인 계정과 철회된 미학습 리플레이가 데이터셋에 포함되지 않는다.
- 닉네임, 프로필 ID, 채팅이 학습용 산출물에 없음을 자동 검사한다.
- 반출과 학습 완료의 경계를 운영 기록으로 확인할 수 있다.

## 5. 권장 실행 순서

1. 원본 리플레이와 평가 워커의 의존 관계를 해소한다.
2. 원본 삭제 상태 머신과 보관기간 자동 파기 배치를 구현한다.
3. 신고 자동 블라인드를 트랜잭션으로 묶고 신고자 해시에 TTL을 적용한다.
4. 온보딩과 정책 변경 안내를 구현한다.
5. 탈퇴 삭제 작업의 재시도·완료 확인을 보강한다.
6. AI 학습을 실제로 시작하기 전에 C3 데이터 생명주기를 구현한다.
7. 모든 항목의 운영 종단 검증 후 개인정보 처리방침의 확정 문구를 갱신한다.
