# BPM_Site 리뉴얼 — 구조·무드 제안서

> **결정 기록 (2026-10-27)** — 이 문서는 제안 당시의 기록이며 아래 본문은 수정하지 않는다.
> - **선택**: 네 안(A~D)을 섞은 `ui-prototype/website`의 디자인을 채택해 Next.js로 이식했다. 코드는 처음부터 다시 만들었다.
> - **라우팅**: `/ko`, `/en` 이중 언어. 라우트는 `/`, `/guide`, `/wiki`, `/patches/[version]`, `/ai`, `/replay-analysis`, `/events`, `/ladder`이다. `/news`는 홈의 소식 영역으로, `/wiki/units/[id]`와 `/wiki/compare`는 위키의 상세 패널(`#유닛id`)과 BPM 유닛 대비 보기로 흡수했다. `/tournaments`, `/report`는 만들지 않았다.
> - **0.1 제약 3번(런처 언급 금지)은 바뀌었다**: 런처는 v2.0 Replay Analysis용으로 소개하되, 배포 전에는 설치 링크 없이 "준비 중"으로 표기한다(`PRODUCT.md`).
> - **0.3 데이터 설계는 다르게 구현했다**: 패치노트는 구조화 데이터가 아니라 사용자가 쓴 Markdown(`content/patches`)이고, 위키는 모드 XML과 실제 게임 덤프에서 만든 `data/generated/wiki.json`이다. 변경 표시는 스냅샷 자동 비교가 아니라 패치노트에서 옮긴 `known-changes.json`을 쓴다.
> - **버전**: 현재 v2.0, 이전 v1.4.3과 v1.4.1(실제로는 v1.4.2_Fix4 추출본)이다. PTR 축은 아직 없다.

- **작성일**: 2026-10-04
- **상태**: 제안 단계 (코드 변경 없음). 하나를 고르거나 조합을 지정하면 다음 단계(상세 설계 → 처음부터 리빌딩)로 진행한다.
- **전제**: 기존 코드는 재사용하지 않고 처음부터 다시 만든다. 데이터(`data/*.json`)와 원본 문서(`docs/`, `base_balance_data_LOTV/`)는 자산으로 유지한다.
- **참고 레퍼런스**: Awwwards(메인·히어로 섹션), Behance·Dribbble(UI 컴포넌트). 아래 레퍼런스 언급은 해당 사이트에서 흔히 보이는 패턴을 가리키며, 특정 작품을 복제한다는 뜻이 아니다.

## 0. 공통 전제 (모든 안에 적용)

### 0.1 반드시 지킬 제약 (PRODUCT.md 기준)
1. **한국어/영어 동시 제공** — 영어는 후속 작업이 아니라 기본 요구사항. 라우팅은 `/ko/...`, `/en/...` 구조를 전제로 한다.
2. **수치 누락 금지** — 위키에서 요약 때문에 값이 사라지면 안 된다. "한눈에 보이되 전부 보인다"가 최우선 요구.
3. **런처는 언급하지 않는다** — 아직 제공되지 않으므로 어떤 화면·문구에도 설치/다운로드 안내를 넣지 않는다.
4. **없는 데이터는 만들지 않는다** — 래더 순위, 대회 결과, 후기, 사용자 수 등 가짜 수치를 UI에 채워 넣지 않는다. 예정 기능은 "준비 중" 상태로 정직하게 표시한다.
5. **확장 가능한 정보 구조** — 래더·대회·버그 리포트·AI 소개가 나중에 추가돼도 기존 위키·패치 구조가 깨지지 않아야 한다.

### 0.2 필수 기능 4종 → 공통 사이트맵 골격

| # | 필수 기능 | 라우트(안) | 핵심 질문 |
|---|---|---|---|
| 1 | 전체 소개 (랜딩 + 뉴스) | `/` , `/news` | BPM이 뭐고, 지금 무슨 일이 있나? |
| 2 | 구체적 소개 (로비 옵션별 실행 방법) | `/guide`, `/guide/[topic]` | 방을 어떻게 만들고 옵션을 어떻게 켜나? |
| 3 | 전체 위키 (종족/유닛별 전 수치) | `/wiki`, `/wiki/[race]`, `/wiki/units/[id]`, `/wiki/compare` | 이 유닛의 모든 수치는? 페어 유닛과 뭐가 다른가? |
| 4 | 버전별 패치 내역 | `/patches`, `/patches/[version]` | 어떤 값이 어떻게 바뀌었나? |

### 0.3 공통 데이터 설계 원칙 (어느 안을 고르든 동일)
- **단일 진실 원천**: 유닛 수치는 하나의 정규화 스키마로 두고, 위키 화면·비교·패치 diff가 모두 같은 데이터를 읽는다. (현재 `units.json`, `standard_units.json`, `modified_units.json`, `ptr_diffs.json`로 흩어진 것을 정리)
- **패치 ↔ 위키 양방향 링크**: 패치 항목에서 해당 유닛 페이지로, 유닛 페이지에서 "이 유닛이 바뀐 이력"으로 이동.
- **버전 스위처**: 위키를 "현재 버전 / 과거 버전 / 다음 버전(PTR)"으로 볼 수 있게 설계 단계에서 데이터에 버전 축을 포함.
- **수치 밀도 3단계 뷰**: ① 요약 카드 ② 전체 수치표(기본) ③ 원본 XML 필드 단위(전문가용). 요약 뷰에서도 숨겨진 값은 "펼치기" 한 번으로 모두 접근 가능해야 한다.

## 안 A. Command Console — "전술 콘솔"

### A.1 컨셉
사이트 전체를 스타크래프트 II의 지휘 인터페이스처럼 구성한다. 사용자는 정보를 "읽는" 게 아니라 콘솔을 "조작"한다. 위키의 유닛 페이지는 유닛 선택 시 나오는 정보 패널의 확장판이다.

### A.2 무드 키워드
`tactical` · `precise` · `dark UI` · `instrument panel` · `cold glow`

### A.3 비주얼 방향
- **색**: 거의 검정에 가까운 남청 배경(`#0A0E14` 계열). 종족 시그널 컬러 3종(테란 = 청, 프로토스 = 금/시안, 저그 = 자홍/보라)을 **의미 있는 곳에만** 사용. 변경 수치 표시용 증가/감소 색(초록/적색 계열)은 종족색과 분리.
- **타이포**: 제목은 각진 디스플레이 산세리프, 본문은 가독성 높은 산세리프, **수치는 모노스페이스 + 탭 숫자**. 한글은 Pretendard 계열, 영문 디스플레이는 별도 선정.
- **형태**: 1px 헤어라인 테두리, 모서리를 살짝 깎은 패널, 미세한 스캔라인/그리드 질감. 과한 네온·글로우 지양.
- **모션**: 패널이 "부팅"되듯 순차 등장, 수치 변경 시 카운터 틱, 호버 시 정보 패널 슬라이드. `prefers-reduced-motion` 대응.

### A.4 히어로 (Awwwards 참고 포인트: 풀뷰포트 + 인터랙티브 단일 오브젝트)
- 풀스크린 어두운 배경에 **밴 슬롯 5개가 상단에 늘어선 HUD**. 스크롤/마우스 입력에 따라 슬롯이 하나씩 "BAN" 처리되고, 마지막에 히든 픽 슬롯이 열리는 짧은 시퀀스.
- 좌하단: 현재 버전 배지(`v1.4.1`)와 "패치노트 보기". 우하단: "가이드 시작하기".
- 카피는 `site_meta.json`의 헤드라인("밴으로 흔들고, 히든 픽으로 완성하는 전장")을 출발점으로 한다.

### A.5 사이트 구조

```
/                 Landing: 히어로 → 핵심 3요소(밴/히든픽/확장유닛) → 최근 뉴스 → 최신 패치 요약 → 위키 진입
/news             뉴스 목록 / /news/[slug]
/guide            로비 옵션 콘솔: 옵션 카드(밴 수, 편의성 모드, 옵저버, 맵) 선택 → 단계별 안내
/wiki             종족 선택(3열) → 유닛 그리드 → 상세 패널
/wiki/units/[id]  유닛 정보 패널(전 수치), 페어 비교, 업그레이드, 변경 이력
/wiki/compare     최대 4유닛 나란히 비교
/patches          버전 타임라인(좌 레일) + 상세(우)
/ladder /tournaments /report /ai   (예약, 동일 콘솔 셸 안에서 "OFFLINE" 상태 표기)
```

### A.6 핵심 UI 컴포넌트 (Behance/Dribbble 참고 포인트)
- **사이드 레일 내비게이션**: 좌측 고정 세로 레일(아이콘 + 라벨), 현재 위치 표시. 모바일에서는 하단 탭바.
- **데이터 패널 카드**: 헤더 스트립(유닛명/종족/티어) + 2열 스탯 그리드 + 하단 탭(능력/업그레이드/이력).
- **커맨드 팔레트(⌘K / Ctrl+K)**: 유닛·버전·옵션 즉시 검색. 운영자·플레이어가 "빠르게 찾기"를 해결.
- **옵션 토글 시뮬레이터**: 가이드에서 로비 옵션을 켜고 끄면 실제 로비 화면이 어떻게 보이는지 미리보기.
- **Diff 칩**: `▲ +5` / `▼ -10` 형태의 값 변경 표시.

### A.7 위키 화면 처리 (요구사항: 한눈에 + 전 수치)
- 종족 탭 → 유닛 **밀집 매트릭스** (행 = 유닛, 열 = HP/방어/공격/사거리/속도/비용/인구/생산시간 …). 열 그룹 접기/펴기, 열 고정, 정렬·필터.
- 행 클릭 시 우측 도킹 패널에 **전 수치 + 능력 + 업그레이드** 표시(페이지 이동 없이 비교 탐색).
- 기본 열 세트는 "전체"로 시작하고, 사용자가 줄이는 방식(기본값이 생략이 되지 않도록).

### A.8 패치 화면 처리
좌측 버전 레일(스크롤 시 현재 버전 강조), 우측에 종족별로 그룹화된 변경 목록. 각 항목은 `이전값 → 새값` 형태이며 위키 링크 포함. 버전 간 비교(from–to) 모드.

### A.9 장단점
- ＋ 게임과의 정서적 연결이 가장 강하고, 위키의 "툴 같은 느낌"이 자연스럽다.
- ＋ 대회/래더 화면도 같은 콘솔 언어로 확장 가능.
- － 다크 + 청색 + HUD는 게임 사이트의 전형이라 차별화에 노력이 필요 (히어로 인터랙션과 타이포로 보완).

## 안 B. Patch Gazette — "패치 가제트"

### B.1 컨셉
BPM을 하나의 **연재되는 매체**로 다룬다. 패치노트는 기사, 버전은 호(issue), 유닛 위키는 도감 부록. Awwwards 수상작에서 자주 보이는 대형 에디토리얼 타이포 중심 레이아웃을 따른다.

### B.2 무드 키워드
`editorial` · `warm paper` · `oversized type` · `confident` · `literary`

### B.3 비주얼 방향
- **색**: 따뜻한 오프화이트/종이색 배경 + 짙은 잉크색 텍스트 + **포인트 컬러 1개**(예: 주황 또는 빨강 계열)만 사용. 종족 구분은 색이 아니라 작은 기호/라벨로 처리. 다크 모드는 별도 토큰으로 제공.
- **타이포**: 제목은 대비가 큰 세리프 또는 개성 있는 그로테스크를 매우 크게(뷰포트 폭 기준 유동 크기). 본문은 가독성 좋은 산세리프. 수치는 탭 숫자 모노.
- **형태**: 얇은 룰 라인, 12컬럼 그리드, 넉넉한 여백, 이미지는 최소(유닛 아이콘/게임 스크린샷은 흑백 처리 또는 하프톤).
- **모션**: 텍스트 라인 마스크 리빌, 스크롤 연동 가로 마퀴, 섹션 전환은 절제.

### B.4 히어로 (Awwwards 참고 포인트: 거대 타이포 + 단일 카피)
- 화면 폭을 가득 채우는 **"BAN. PICK. PLAY."** 류의 초대형 워드마크와 현재 호수(`ISSUE v1.4.1 — 2026.09.14`).
- 하단 한 줄에 "이번 호 헤드라인(최신 패치 제목)"과 3개의 진입 링크.
- 히어로 이후 스크롤 시 "이번 호 목차(Table of Contents)" 형태로 사이트 전 섹션을 소개.

### B.5 사이트 구조

```
/                 Landing: 워드마크 → 이번 호 목차 → 헤드라인 기사 → 규칙 3줄 요약 → 지난 호 → 위키 진입
/news             "특집/공지" 기사 목록
/guide            "How to play" 챕터식 연재: 1장 방 만들기 · 2장 밴 설정 · 3장 편의성 · 4장 옵저버 …
/wiki             "도감 부록": 종족 장 → 유닛 항목 (인덱스 + 색인)
/wiki/units/[id]  한 장짜리 도감 페이지(큰 이름 + 전체 수치표 + 변경 이력 각주)
/patches          호(issue) 아카이브 / /patches/[version] 기사 형태의 패치노트
/ladder /tournaments /report /ai   (예약, "곧 발행" 표기)
```

### B.6 핵심 UI 컴포넌트
- **인덱스 리스트 내비게이션**: 풀스크린 오버레이 목차(큰 글씨 항목, 호버 시 미리보기 이미지/문장).
- **기사 레이아웃**: 좌측 메타(버전, 날짜, 태그), 중앙 본문, 우측 각주/관련 위키 링크 (Dribbble의 에디토리얼 UI 패턴).
- **변경 기사 블록**: 변경 항목을 "이전 → 이후" 타이포그래피 대비(취소선 + 굵은 새 값)로 표현.
- **색인(Index)**: 위키 하단의 A–Z/가나다 색인 및 종족별 색인.

### B.7 위키 화면 처리
- 종족별 **도감 인덱스**(표 형태의 촘촘한 목록)와 개별 유닛 **한 장 페이지**. 표는 문서의 표처럼 선과 여백으로 구분해 가독성을 확보.
- 약점: 많은 유닛을 한 화면에서 가로로 비교하는 데는 콘솔형보다 불리하므로, `/wiki/compare`를 더 강하게 밀어준다.

### B.8 패치 화면 처리
이 안의 최대 강점. 각 패치가 하나의 "기사"이며, 상단에 한 문단 요약, 이후 종족별 섹션, 맨 끝에 "전체 변경 수치 표"를 둔다. 서술형 + 수치형 두 독서 방식을 모두 지원.

### B.9 장단점
- ＋ 차별화가 가장 크고, 뉴스·패치노트·가이드 같은 **읽는 콘텐츠**가 매력적으로 보인다.
- ＋ 구현이 비교적 가볍고 성능 부담이 작다.
- － 데이터 중심 위키는 "표"가 주인공이라 연출이 약해질 수 있어, 위키 전용 밀도 있는 레이아웃을 따로 설계해야 한다.

## 안 C. Draft Arena — "드래프트 아레나"

### C.1 컨셉
BPM의 정체성인 **밴픽 그 자체**를 사이트 전체의 연출 언어로 삼는다. e스포츠 중계 화면(밴픽 단계 오버레이)의 대비·에너지·스포트라이트를 웹으로 가져온다. 대회·래더 확장에 가장 어울린다.

### C.2 무드 키워드
`broadcast` · `spotlight` · `high contrast` · `kinetic` · `stage lighting`

### C.3 비주얼 방향
- **색**: 짙은 배경 위에 **양 팀 대비색 2개**(예: 청 vs 적)를 축으로 삼고, "BAN"은 빨강+사선/취소선, "PICK"은 밝은 톤의 하이라이트. 종족색은 보조.
- **타이포**: 굵은 이탤릭/컨덴스드 디스플레이로 에너지 부여, 본문은 중립 산세리프, 수치는 모노.
- **형태**: 사선 컷(대각선 패널), 스포트라이트 그라데이션, 유닛 아이콘/컷아웃 대형 배치, 카드가 뒤집히는 플립.
- **모션**: 가장 풍부. 밴 스탬프 효과, 카드 리빌, 스크롤 연동 핀 고정 시퀀스. 단 위키·패치 페이지는 연출을 의도적으로 낮춘다("무대"와 "도서관" 분리).

### C.4 히어로 (Awwwards 참고 포인트: 스크롤 시퀀스형 스토리텔링)
- 스크롤 핀 고정 시퀀스: **① 17종 유닛이 격자로 등장 → ② 밴이 하나씩 스탬프 → ③ 남은 선택지 중 하나가 어둡게 가려진 "히든 픽"으로 확정 → ④ "BAN. HIDE. WIN." 카피**.
- 스크롤을 내리면 밴 수 선택(0/1/3/5)에 따라 그리드가 바뀌는 인터랙티브 데모.
- 유닛 아이콘은 `public/assets/images/icons/`의 기존 자산 활용 가능.

### C.5 사이트 구조

```
/                 Landing: 스크롤 시퀀스 → 규칙 3스텝 → 라이브/최근 소식 → 최신 패치 → 위키 진입
/news             이벤트/소식 피드 (대회 알림 확장 전제)
/guide            "Lobby Setup" 스텝 위저드: 맵 → 밴 수 → 편의성 → 옵저버 (옵션 조합별 결과 미리보기)
/wiki             "Roster": 종족 3분할 → 유닛 카드 월
/wiki/units/[id]  선수 프로필 카드 스타일의 유닛 페이지 + 전 수치 표
/wiki/compare     Versus 화면(좌/우 대결형 비교)
/patches          시즌/버전 타임라인
/tournaments      (예약 → 확장 시 핵심 축) 브래킷/매치/드래프트 리플레이
/ladder           (예약) 랭킹
/report /ai       (예약)
```

### C.6 핵심 UI 컴포넌트
- **밴 슬롯 컴포넌트**: 재사용 가능한 `BanSlot` / `PickSlot`을 사이트 전반(랜딩 데모, 가이드, 대회 페이지)에서 공유.
- **Versus 비교**: 두 유닛을 좌우로 배치하고 수치 막대가 중앙에서 양쪽으로 뻗는 비교 UI (Dribbble 대시보드 패턴).
- **스텝 위저드**: 로비 옵션 선택을 단계형 카드로. 마지막에 "당신의 로비 설정 요약"을 공유 가능한 형태로 표시.
- **스탬프/토스트 피드백**: 상태 변화를 짧은 연출로 알림.

### C.7 위키 화면 처리
- "Roster" 월에서 카드로 탐색하되, **카드 하단에 핵심 수치가 이미 노출**되고 클릭하면 전 수치 표가 있는 프로필 페이지로.
- 연출 과다 방지를 위해 `/wiki`는 "표 보기 / 카드 보기" 토글을 두고, **표 보기를 데이터 열람용 기본값**으로 둘 수 있도록 설계.

### C.8 패치 화면 처리
버전별로 "경기 후 요약" 같은 대형 헤더 + 변경 목록. 밸런스 변경이 큰 유닛은 상단 하이라이트 카드(이전/이후 값 대비).

### C.9 장단점
- ＋ 방문 첫 10초 임팩트가 가장 크다. 대회·래더가 붙을수록 사이트의 정체성이 선명해진다.
- ＋ BPM만의 차별점(맵 내부 밴픽)을 시각 언어로 직접 번역.
- － 모션·인터랙션 구현 비용이 가장 크고, 성능·접근성(모션 축소, 키보드) 설계 부담이 크다.
- － 위키/패치에서 연출을 얼마나 낮출지 기준을 명확히 정해야 한다.

## 안 D. Field Manual — "필드 매뉴얼"

### D.1 컨셉
BPM을 **공식 기술 매뉴얼 + 데이터시트 아카이브**로 다룬다. "수치가 빠짐없이, 한눈에" 요구에 가장 직접적으로 답하는 안. 대회 운영자와 심판이 근거 문서로 쓰기 좋은 신뢰감이 목표.

### D.2 무드 키워드
`datasheet` · `swiss grid` · `monospaced` · `utilitarian` · `declassified blueprint`

### D.3 비주얼 방향
- **색**: 밝은 회백색(또는 짙은 먹색) 배경에 검정/회색 잉크, 포인트 컬러 1개(형광 계열 또는 경고 주황). 컬러보다 **선과 타이포**로 위계를 만든다.
- **타이포**: 스위스 스타일 그로테스크 + 모노스페이스 병용. 제목과 본문의 크기 대비를 극단적으로 사용(작은 라벨 + 큰 숫자).
- **형태**: 엄격한 컬럼 그리드, 표 중심, 도면식 레이블(`FIG. 03`, `REF: v1.4.1`), 모서리 라운드 없음 또는 최소.
- **모션**: 최소. 정확한 전환과 포커스 표시, 숫자 정렬/하이라이트 중심. 느린 연출은 사용하지 않는다.

### D.4 히어로 (Awwwards 참고 포인트: 정보형 미니멀 히어로)
- 좌측: 큰 타이포 한 줄 + 한 문단 정의. 우측: **현재 빌드 데이터시트**(버전, 날짜, 유닛 수, 지원 맵 수, 밴 옵션 0·1·3·5)가 표로 정렬된 "스펙 시트".
- 하단에 검색창 하나(유닛·버전·옵션 통합 검색). "뭐든 바로 찾기"가 히어로의 CTA.

### D.5 사이트 구조

```
/                 Landing: 스펙 시트 히어로 + 통합 검색 → 기능 4종 인덱스 → 최신 패치 diff 미리보기 → 최근 뉴스
/news             공지 로그(날짜순 리스트)
/guide            "Procedures": 번호가 매겨진 절차 문서 (예: 3.2 밴 개수 설정). 옵션별로 독립 페이지
/wiki             "Data Sheets": 종족 → 유닛 마스터 테이블(전 열 노출)
/wiki/units/[id]  유닛 데이터시트 1페이지(전 필드, 출처 XML 필드명 병기 가능)
/wiki/compare     N-way 비교 테이블
/patches          Changelog: 버전 목록 + 필터(종족/유닛/카테고리)
/patches/[ver]    정규화된 diff 표(대상 / 항목 / 이전 / 이후 / 비고)
/ladder /tournaments /report /ai   (예약, "Reserved" 섹션)
```

### D.6 핵심 UI 컴포넌트
- **마스터 테이블**: 가상 스크롤, 열 그룹 접기, 열 고정, 정렬·다중 필터, CSV 내보내기, 현재 뷰 URL 공유. 수치 밀도가 가장 높은 설계.
- **Diff 표**: 변경 항목마다 `이전 / 이후 / Δ` 열. 밸런스 변경을 한눈에 스캔.
- **고정 목차(TOC) 사이드바**: 긴 절차·데이터시트 문서의 앵커 이동.
- **참조 배지**: `REF`, `SINCE v1.4`, `CHANGED v1.5`처럼 데이터마다 출처/이력을 붙여 신뢰감 확보.

### D.7 위키 화면 처리
요구사항 "모든 구체적 수치를 종족/유닛별로 한눈에, 하지만 전부 보이게"에 가장 정직한 해법. 요약을 위한 생략이 없고, 사용자가 필터로 줄이는 구조.

### D.8 패치 화면 처리
패치를 "표준화된 변경 레코드"의 집합으로 취급. 버전·종족·유닛·카테고리 필터와 from–to 비교가 쉽다. 자연어 요약은 상단에 짧게만 둔다.

### D.9 장단점
- ＋ 정확성·검색성·확장성 원칙에 가장 정합. 구현이 단순하고 성능이 좋다.
- ＋ 운영자·심판용 근거 문서로 신뢰감이 높다.
- － 첫인상이 차갑다. 신규 플레이어를 끌어들이는 힘은 약하므로 랜딩과 가이드에 따뜻한 요소(예: 스크린샷, 짧은 영상)를 보강해야 한다.

## 추천 및 조합안

**1순위 추천: C 랜딩 × A 콘솔 위키 × D 테이블 밀도 (하이브리드)**

| 영역 | 채택 안 | 이유 |
|---|---|---|
| 랜딩·뉴스 | C (Draft Arena) | 밴픽이라는 정체성을 첫 화면에서 전달. 대회 확장성 최고 |
| 가이드 | C의 스텝 위저드 + D의 절차 문서 | 시각 미리보기 + 정확한 단계 기술 |
| 위키 | D의 마스터 테이블 + A의 도킹 패널 | "한눈에 + 전 수치"를 가장 충실히 충족 |
| 패치 | B의 기사형 헤더 + D의 diff 표 | 읽는 재미와 정확성 동시 확보 |
| 예정 기능(래더·대회) | C의 Versus/브래킷 언어 | 이미 사이트 언어와 일치 |

핵심 규칙: **"무대(랜딩·대회·래더)는 극적으로, 도서관(위키·패치·가이드)은 조용하고 정확하게."** 같은 디자인 토큰을 공유하되 연출 강도만 영역별로 다르게 둔다.

**단일 안으로 가야 한다면**: 개발·유지 비용과 요구사항 정합성을 우선하면 **A**(균형), 차별화와 임팩트를 우선하면 **C**, 정확성·검색성을 우선하면 **D**.

## 배포 방식 제안 (추후 선택)

데이터가 전부 저장소 안의 JSON/MD이고 서버 로직이 필요 없으므로 **정적 사이트(Next.js static export)** 가 기본 전제입니다. 래더·대회·버그 리포트가 실데이터를 요구하는 시점에 서버 기능을 추가합니다.

| 방식 | 장점 | 단점 | 추천 상황 |
|---|---|---|---|
| **Cloudflare Pages** (추천) | 무료, 대역폭 제한 사실상 없음, 한국 엣지 빠름, 나중에 Workers/D1으로 래더·버그 리포트 확장 쉬움, 커스텀 도메인 무료 | 서버 기능은 Workers 방식 학습 필요 | 정적 시작 → 래더/제보 확장 |
| Vercel | Next.js와 궁합 최고, PR 프리뷰 | 무료 플랜 상업 이용 제한, 대역폭 한도 | Next 서버 기능을 많이 쓸 때 |
| GitHub Pages | 완전 무료, 기존 저장소와 한 곳 | 서버 기능 불가, 기존 사이트가 이미 사용 중이면 교체 필요 | 끝까지 정적으로만 갈 때 |
| 자체 VPS (Docker) | 완전한 통제, DB·리플레이 업로드 가능 | 운영·보안 부담 | 리플레이 분석·AI까지 직접 호스팅할 때 |

**권장 경로**: 지금은 로컬 → 안정되면 Cloudflare Pages 프리뷰 URL로 공개 테스트 → 래더/버그 리포트 단계에서 Cloudflare Workers + D1(또는 Supabase)로 확장.
