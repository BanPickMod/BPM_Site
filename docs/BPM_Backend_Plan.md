## 0. 요약

v2.0 패치노트는 이미 다음을 약속했다. 백엔드는 이 약속을 지키는 것이 최우선 목적이다.

1. **[확정]** 로그인 + 리플레이 제공 동의를 한 사용자에게만 Replay Analysis를 제공한다.
2. **[확정]** PatchesSC처럼 리플레이를 자동 업로드하는 런처를 설치해야 동작한다.
3. **[확정]** 업로드된 리플레이는 AI가 실시간으로 분석해 밴픽과 플레이를 평가한다.
4. **[확정]** 제3자 공개 여부는 본인이 선택한다.
5. **[확정]** AI 학습 사용은 별도 동의를 한 경우에만 허용한다. 그 외에는 학습·제3자 제공에 절대 쓰지 않는다.
6. **[확정]** 동의한 사용자의 데이터로만 플레이어 밴픽 비율을 보여주고, AI의 밴픽/승률 정보와 함께 제공한다.
7. **[확정]** 이벤트: BPM AI 콜로세움 1(11/1~11/2 KST), BPM AI Challenge S1(일정 TBD, 시스템 자동 집계).
8. **[확정]** 이후 BPM 래더로 확장한다.

초기 구현은 콜로세움용 운영자 경로를 Phase 0으로, 사용자 계정·업로드를 Phase 1로 나눠 진행했다. 현재 코드에는 두 경로와 C2 공개·통계·리플레이 뷰어까지 들어가 있다. 다만 운영 배포 종단 검증, 정식 개인정보 안내, 업로더 배포, AI 평가는 남아 있다.

## 1. 목표와 비목표

### 1.1 목표
- 동의한 사용자의 리플레이를 안정적으로 수집하고, 사용자 본인에게 AI 분석을 보여준다.

- Tournament Engine(Match/Game 상태 머신, 룰 엔진, 관리자 override 전체). 이벤트 집계에 필요한 최소 관리자 기능만 만든다.
- 게임 안(Galaxy)에서 서버로 직접 통신. `BPM_Platform_Plan.md` §10.1의 전제를 유지한다.
- 래더 레이팅·매칭. 데이터만 래더로 확장 가능하게 둔다.
- 실시간 라이브 관전.

## 2. 동의와 개인정보 모델 (설계의 중심)

패치노트의 문장을 그대로 데이터 권한으로 옮긴다. 동의는 **3단 독립 스위치**로 둔다. 높은 단계가 낮은 단계를 자동으로 켜지는 않는다(업로드는 모두의 전제).

| 단계 | 이름 | 허용 | 기본값 |
|---|---|---|---|
| C1 | 분석용 업로드 | 서버에 저장, 본인에게 AI 분석 제공. 본인 외 누구도 접근 불가 | 로그인 시 필수 선택(끄면 서비스 이용 불가) |
| C2 | 공개 열람 | 제3자가 리플레이 분석 페이지와 리플레이 파일을 볼 수 있음. **집계 통계(밴픽 비율)에도 포함** | 꺼짐 |
| C3 | AI 학습 허용 | 학습 데이터셋 후보에 포함 | 꺼짐 |

**[제안] 쟁점 1: 밴픽 비율 통계 포함을 C2에 묶을지 별도(C4)로 둘지.** 패치노트는 "제공 동의가 된 분들의 데이터만 기반"이라고만 했고 C2와 같은 것인지 명시하지 않았다. 대안은 "통계는 익명 집계이므로 C1 이상이면 포함"이다. 권장은 보수적으로 **C2에 포함**하는 안이다. 통계는 개인을 특정하지 않지만 "제공 동의"의 의미를 좁게 해석해야 약속을 어길 위험이 없다. 단 이 경우 표본이 줄어 통계가 늦게 쌓인다. → **결정(2026-10-27): C2에 포함.**

### 2.1 규칙
1. 동의는 **리플레이 단위로 스냅샷**한다. 업로드 시점의 동의 상태를 `replay_consent`에 저장하고, 사용자가 이후 설정을 바꾸면 기존 리플레이에도 반영할지 선택하게 한다(철회는 모든 기존 리플레이에 즉시 적용한다. 재허용은 기존 리플레이에 소급하지 않고, 사용자가 리플레이별로 공개를 켠다. 2026-10-28 변경: 이전 기본은 소급 적용이었으나 비공개로 둔 경기가 다시 공개되는 결함이 있었다).
2. **철회는 즉시 효력**이다. C2 철회 시 공개 조회·집계 대상에서 제외하고, C3 철회 시 아직 학습에 쓰이지 않은 후보에서 제외한다. 이미 학습된 모델에서 데이터를 제거할 수는 없으므로, 약관에 "철회 이전에 학습된 모델 가중치에서는 제거되지 않는다"를 명시한다.
3. **학습 파이프라인은 동의 필터를 서버가 건 뷰(`v_training_eligible`)로만 읽는다.** 학습 코드(`bpm-ai-engine`, 별도 비공개 저장소)는 원본 테이블에 접근하지 못한다. 이것이 "절대 활용되지 않는다"는 약속의 기술적 근거다.
4. 모든 동의 변경과 접근을 감사 로그에 남긴다.
5. 계정 삭제 시 리플레이 원본·분석 결과를 삭제하고, 집계 통계는 재계산한다. 이벤트 수상 기록은 법적·운영 사유로 별도 보존 정책을 둔다(약관에 명시).

### 2.2 리플레이에 들어 있는 개인정보
`.SC2Replay`에는 닉네임, Battle.net 프로필 ID(핸들), 채팅이 들어 있다. 공개 시 처리 규칙:
- **[제안]** C2 공개 시 표시 이름은 사이트 프로필 이름을 쓰고, 파일 다운로드를 허용하면 원본의 핸들이 노출된다. **결정(2026-10-27): 사용자 리플레이의 원본 다운로드는 금지**한다(개인정보 우려). 사용자 리플레이는 서버가 만든 분석 페이지로만 공개하며, 원본 파일은 업로더 본인에게도 다시 내려주지 않는 것을 기본으로 한다(본인 재다운로드 허용 여부는 열린 항목). 다운로드는 사람이 없는 콜로세움(AI 대 AI) 리플레이에 한정한다.
- 채팅 로그는 분석에 필요 없으면 공개 화면에서 제외한다.
- 상대(제3자) 플레이어의 정보: 리플레이에는 상대 닉네임도 있다. 상대는 동의한 적이 없으므로 **공개 화면에서 상대 이름은 가림 처리**(예: "상대 플레이어")를 기본으로 한다(결정: 권장안대로).

### 2.3 법적 고려 (확인 필요, 법률 자문 아님)
- 한국 개인정보 보호법: 수집 항목·목적·보유 기간 고지, 수집·이용 동의, 제3자 제공 동의가 필요하다. C1/C2/C3는 목적별 분리 동의여야 한다.
- **결정·구현 (2026-10-28)**: 만 14세 미만의 가입·이용을 제한한다. 최초 Battle.net 로그인 전에 만 14세 이상 자기확인을 필수로 받고 확인 시각만 저장하며 생년월일은 수집하지 않는다. 기존 계정은 다음 설정·런처 연결 전에 같은 확인을 받는다.
- 해외 사용자(영어 지원 필수)가 있으므로 GDPR 수준의 삭제·열람 요청 절차를 같이 둔다.
- 상금(예: 30만원)은 세금(기타소득 원천징수 등)과 수령자 신원 확인 문제가 있다. 수상자 정보는 이벤트 운영 시 별도 수집하며 사이트 DB 계정 정보와 분리한다.
- 약관·개인정보 처리방침 초안이 **Phase 1 출시 전 필수 선행 작업**이다. 이 문서는 법률 문서를 대체하지 않는다.
- 개인정보 처리방침과 실제 서버 동작을 일치시키기 위한 현재 판정, 우선순위와 완료 조건은 [`Privacy_Compliance_Implementation_Plan.md`](./Privacy_Compliance_Implementation_Plan.md)를 따른다.

## 3. 시스템 구성

```text
 [사용자 PC]                       [BPM 서버]                              [분석 환경]
 SC2 종료                            
   │ .SC2Replay 생성                 API (Next.js Route / 별도 서비스)       Analysis Worker (Python)
 BPM Launcher ──① 로그인(디바이스 코드)──▶ Auth                              ├ s2protocol 디코드
   │  watcher                          │                                       ├ BPM 의미 복원(밴픽·빌드)
   ├─② 업로드 의향(해시)──────────────▶ Upload API ─▶ 중복/자격 검사           ├ 메트릭 추출
   ├─③ 사전 서명 URL로 PUT ──────────▶ Object Storage (비공개)                  └ bpm-ai-engine 평가(GPU)
   └─④ 완료 통지 ─────────────────────▶ Queue ─────────────────────────────────▶ 결과 ─▶ DB
                                         │
 [웹 사이트] ◀── 분석·통계 조회 ──────── DB (Postgres) ◀── 집계 잡(Aggregator)
 [운영자 콘솔] ── 이벤트 수집·검수·집계 ─▶ 관리자 API
```

### 3.1 컴포넌트

| 컴포넌트 | 책임 | 비고 |
|---|---|---|
| **BPM Launcher** | 리플레이 폴더 감시, 쓰기 완료 판정, 해시 계산, 업로드, 동의 설정 표시, 자동 업데이트 | `BPM_Platform_Plan.md` §6의 Companion을 v2.0 범위(업로드 중심)로 축소. 기존 CONTRIBUTING의 "런처는 게임 룰 판정 ✗" 원칙 유지 |
| **API 서버** | 인증, 동의 관리, 업로드 승인, 조회, 관리자 기능 | 아래 §3.2 |
| **Object Storage** | 리플레이 원본 보관(비공개 버킷) | 서명 URL로만 읽기/쓰기 |
| **Queue + Worker** | 비동기 분석. 업로드와 분석을 분리해 실패를 격리 | 업로드 파일은 신뢰하지 않는다(파서 오류 격리) |
| **DB (Postgres)** | 사용자·동의·리플레이 메타·분석 결과·집계·이벤트 | JSONB로 분석 세부 저장 |
| **Aggregator** | 동의 필터를 통과한 데이터로 밴픽 비율·승률 집계 | 주기 잡 + 증분 갱신 |
| **운영자 콘솔** | 이벤트 리플레이 수집, 검수, 집계 확정, 상금 후보 확정 | v2.0에서는 최소 UI |

### 3.2 기술 선택 [제안]

현재 사이트는 Next.js 16(App Router, `proxy.ts`) 정적 중심이고 `.github/workflows/deploy-pages.yml`은 GitHub Pages 배포다. **GitHub Pages는 서버 기능을 못 하므로 백엔드를 얹으려면 호스팅 변경이 필요하다.**

**결정(2026-10-27): Railway를 사용한다.** 권장 배치:
- 서비스 1: Next.js 웹+API (Node 서비스, 기존 코드 그대로)
- 서비스 2: Postgres (Railway 관리형, 큐도 겸함)
- 서비스 3: 경량 Python 워커(파싱·메트릭 추출). GPU가 필요한 AI 평가는 Railway에서 돌리지 않고 로컬/전용 GPU 머신이 큐를 풀링한다(§5.4).
- 스토리지: 리플레이 원본은 Cloudflare R2(S3 호환, 이그레스 무료)를 권장. Railway 자체 볼륨/버킷은 서비스 종속·백업 면에서 원본 보관용으로 덜 적합하다고 보나, 제공 기능은 가입 시점에 확인한다.
- 장점: 배포가 간단하고 Postgres·환경변수·프리뷰 환경이 한곳에 있어 1인 운영에 맞다. 주의: 사용량 과금이라 업로드 폭주·분석 루프에 상한(§4.5)을 꼭 걸 것. 지역(리전) 선택이 한국 사용자 지연에 영향을 주므로 가장 가까운 리전을 확인한다.
- 정적 공개 페이지(위키·패치)는 Railway 서버가 감당하면 되지만, 트래픽이 커지면 CDN(Cloudflare)을 앞에 둔다.

| 영역 | 권장안 | 이유 |
|---|---|---|
| API | Next.js Route Handlers + 별도 Python 분석 워커 | 기존 코드 재사용. 분석은 Python(s2protocol, bpm-ai-engine)이 필요해 분리 |
| DB | Postgres (관리형) | 동의 필터 뷰, 집계, JSONB |
| 스토리지 | S3 호환(예: Cloudflare R2) | 이그레스 비용 낮음, 서명 URL |
| 큐 | Postgres 기반 큐(예: pg-boss류) 우선 | 초기 규모에서 별도 브로커 불필요. 병목이 보이면 교체 |
| 인증 | OAuth 로그인(Battle.net 또는 Discord 등) + 런처용 디바이스 코드 플로우 | 쟁점 5 참고 |
| 분석 GPU | 로컬/전용 머신의 워커가 큐를 풀링 | 비공개 `bpm-ai-engine` 코드를 클라우드에 올리지 않을 수 있음 |

**쟁점 5: 로그인 제공자.** Battle.net OAuth는 SC2 핸들과 계정을 검증된 상태로 연결할 수 있어 "내 리플레이" 판정과 이벤트 부정 방지에 유리하지만 지역별 앱 등록이 필요하다. Discord는 간편하지만 SC2 신원을 보증하지 않는다. **결정(2026-10-27): Battle.net OAuth를 최우선으로 연결한다.** 구현 시 확인할 점: 개발자 포털에서 클라이언트 등록(지역별 NA/EU/KR 엔드포인트), 받을 수 있는 신원 정보(계정 ID, BattleTag)와 SC2 프로필(리전·렐름·프로필 ID) 조회 가능 여부와 필요한 scope. 계정 ID만 얻고 SC2 프로필 ID를 못 얻으면 리플레이 핸들과의 연결을 사용자 확인 절차로 보완한다. 아래는 폴백이다: 불가하면 Discord + 리플레이 내 핸들을 사용자가 수동 연결·확인하는 방식.

## 4. 업로드 프로토콜

### 4.1 런처 인증
1. 런처가 디바이스 코드를 요청 → 브라우저에서 로그인·승인 → 런처가 장기 토큰(회전 가능)을 받는다.
2. 토큰은 Windows 자격 증명 저장소에 보관한다. 서버는 토큰 단위로 폐기할 수 있다.

### 4.2 업로드 절차
1. 런처가 새 `.SC2Replay`를 감지하고 크기·mtime이 안정될 때까지 기다린다(`BPM_Platform_Plan.md` §6.3).
2. **클라이언트 사전 필터**: BPM 모드 리플레이인지 확인(헤더·의존 모드 정보). 일반 래더 리플레이는 올리지 않는다. 이것은 개인정보 최소 수집이기도 하다.
3. `POST /api/uploads`에 `{sha256, size, game_build, client_version}` 전송.
4. 서버: 인증 → C1 동의 확인 → 해시 중복 검사(같은 리플레이를 두 참가자가 올릴 수 있으므로 §4.3) → 할당량 검사 → 사전 서명 PUT URL 반환.
5. 런처가 스토리지로 직접 업로드, `POST /api/uploads/{id}/complete`.
6. 서버가 크기·확장자·MPQ 시그니처를 재검사하고 분석 큐에 넣는다.
7. 런처는 `GET /api/uploads/{id}/status`로 상태를 표시한다.

### 4.3 같은 경기의 중복
PvP처럼 두 사람이 모두 업로드할 수 있다. 파일 해시는 참가자별 리플레이가 다를 수 있으므로 **경기 지문**(맵 해시, 시작 시각, 참가자 핸들 집합, 총 프레임)으로 `match_fingerprint`를 만들어 같은 경기를 하나의 `game`으로 묶고 업로드를 `replay` 행으로 여러 개 둔다. 동의는 **업로더의 동의만 그 업로더의 파일에 적용**한다. 한 쪽이 C2에 동의하지 않았다면 그 경기의 공개 화면은 동의한 쪽 시점 데이터만 쓴다. 통계 이중 집계는 `game` 단위로 중복 제거한다.

**구현 (2026-10-28)**: 지문은 저장하지 않고 **읽을 때 계산**한다(`lib/replay/matchKey.ts`). 워커가 분석에 `startedAt`(게임 시작 UTC 초)과 `gameLoops`(총 프레임)를 추가로 담고(`analyzerVersion` `timeline-2`), 서버는 `맵 + 참가자 핸들 집합(좌석 무관) + 시작 시각 ±120초 + 길이 ±30초(672프레임)`가 같으면 같은 경기로 본다. 두 클라이언트가 각자 시작 시각과 마지막 프레임을 기록해 값이 조금씩 다르므로 동등 비교가 아니라 허용 범위 비교다. 같은 두 사람의 재대결은 시작 시각이 달라 다른 경기다. 저장하지 않으므로 두 리플레이가 동시에 분석을 마쳐도 그룹이 둘로 갈라지지 않고 소급 작업이 필요 없다.
- **적용처**: 공개 목록(같은 경기는 한 번만, 가장 최근 복사본), 커뮤니티 통계(경기당 1회). 공개 중인 리플레이끼리만 비교하므로 한 업로더가 C2를 철회하면 다른 업로더의 복사본이 남고, 둘 다 철회하면 사라진다. 동의는 업로더별로 따로 적용된다(§4.3 그대로).
- **옛 분석·AI 경기**: 핸들이나 시작 시각이 없으면 지문을 만들 수 없어 예전처럼 맵·길이·종족·결과·드래프트 비교로 대신한다. 둘 다 지문이 있으면 지문이 우선한다(드래프트와 결과가 같아도 시작 시각이 다르면 다른 경기).
- **노출 금지**: 업로더에게 상대도 올렸다는 사실을 알리지 않고, 핸들은 어떤 공개 응답에도 나가지 않는다.
- **한계**: 두 사람 모두 올린 실제 PvP 리플레이로는 시험하지 못했다(실제 시작 시각 오차가 120초 안에 드는지 확인 필요). 규모가 커져 목록·통계를 읽을 때마다 계산하기 부담스러워지면 `match_key`·`started_at` 컬럼을 두고 색인한다. 같은 사용자가 같은 경기의 두 시점(관전 등)을 올리는 경우는 다루지 않는다.

### 4.4 상태 머신
```text
UPLOAD_REQUESTED → UPLOADED → VALIDATING → QUEUED → ANALYZING → READY
                      │            │                    │
                      └─ REJECTED ─┘                    └─ FAILED(retry n) → DEAD
```
거부 사유는 코드화한다: `NOT_BPM`, `DUPLICATE`, `CORRUPT`, `UNSUPPORTED_BUILD`, `TOO_SHORT`, `NO_CONSENT`, `QUOTA`.

### 4.5 제한 [제안]
리플레이 크기 상한(예: 10MB), 사용자별 일일 업로드 상한, 업로드 URL 유효시간 짧게, 확장자·시그니처 이중 검사.

## 5. 분석 파이프라인

패치노트의 "AI가 실시간 분석"은 **업로드 후 수 분 내 결과 제공**으로 정의한다(경기 중 분석이 아님) [제안: 목표 5분 이내 p90, 확정은 부하 측정 후].

### 5.1 단계
1. **안전 파싱**: 격리 프로세스에서 s2protocol로 디코드, 타임아웃과 메모리 상한. `baseBuild`에 맞는 프로토콜 모듈 선택.
2. **BPM 의미 복원**: 밴픽 결과와 로스터를 복원.
3. **메트릭 추출**: 빌드 오더, 일꾼·병력 곡선, 확장 시점, 교전 구간. 이 부분은 이미 `bpm-ai-engine`에 프로 리플레이용 추출 도구(L0: 유닛 생애·위치·10초 통계)가 있으므로 같은 스키마를 재사용한다.
4. **타임라인 묶음 생성**(2026-10-27 추가): 뷰어 재생용 `timeline.json.gz`(유닛 생애, 위치 표본, 시계열, 빌드 표, 교전). 스키마와 크기 목표는 `Replay_Viewer_Plan.md` §6.2. 원본 리플레이는 재생성을 위해 분석 뒤에도 보존한다.
5. **AI 평가**: 학습된 평가자로 밴픽 품질·플레이 평가 점수 산출. 학습이 끝나기 전에는 만들지 않는다.
   - **1단계 검증 결과 (2026-10-28, `bpm-ai-engine/docs/reports/bpm_value_validation.md`)**: 프로 경기로 학습한 평가자를 BPM 리플레이 976판(엔진 AI 경기 922, 사용자의 사람 대 AI 54)에서 재 봤다. 입력 행 어댑터(`src/bpm_ai/evaluation/replay_value.py`)는 학습 표와 값이 99.9% 같고 프로 시험 분할에서 학습 때 지표를 재현한다. **4분 이전은 쓸 수 없고**(사람 경기 AUC 0.48–0.50, 엔진 AI 경기는 0.12로 거꾸로), **8분 이후는 순위로는 쓸 만하지만**(M1 0.83–1.0) 단순 병력 비 기준선과 비슷하며, **확률 값은 과신**(ECE 0.19–0.25)이라 퍼센트로 보이면 안 된다. 경기 후 분석에는 상대 실제 상태까지 쓰는 M1이 낫다.
   - **2단계(사이트 연결) 구현 (2026-10-28)**: 분석이 끝난 리플레이마다 평가 작업이 생기고(`eval_status` PENDING→LEASED→DONE/SKIPPED/FAILED, 분석 큐와 같은 방식의 당겨 가기·10분 임대·재시도 3회), 워커가 M1 기반 **형세 곡선**(10초마다 `a` = 플레이어 1의 형세 − 플레이어 2의 형세, −1~+1, `validated:false`)을 `evaluation`에 저장한다. 재생기 요약 탭 맨 위에 "AI 형세 평가" 카드(곡선, 형세가 크게 바뀐 지점 최대 3곳, 클릭하면 그 시점으로 이동). **4분 전은 표시하지 않고, 4–8분은 흐리게, 8분 이후는 실선**이며 기준은 `lib/replay/evaluation.ts`의 상수라 재계산 없이 바꿀 수 있다. 카드에는 "프로 경기로 학습, BPM 보정 전, 승리 확률 아님"을 적는다. 본인 화면과 공개 화면(C2) 모두 보이고 공개 응답에는 곡선 숫자만 나간다(핸들 없음). 분석이 다시 끝나면 평가도 처음부터 다시 한다.
   - **Railway 배포 준비**: 평가 코드는 엔진 저장소가 아니라 `worker/bpm_eval/`에 **복사본**으로 들어 있어(상태·추출·특징·추론 4개 파일과 역할표, M1 번들 4 MB; 엔진 파일을 그대로 복사, `scripts/sync-eval-from-engine.py`, `--check`로 어긋남 확인) 비공개 엔진 없이 배포된다. 엔진 쪽 `tests/test_vendored_eval.py`가 복사본이 엔진과 같은 해시인지, 같은 리플레이에서 같은 곡선을 내는지(오차 0.0005)를 확인한다. 워커 하나가 분석 큐가 비면 평가 큐를 처리하므로 별도 서비스가 필요 없다(`BPM_EVAL=0`으로 끔). 필요한 것: Python 3.11 이상(3.13에서 확인), `worker/requirements.txt`(s2protocol, mpyq, numpy), 환경 변수 `BPM_SERVER_URL`·`WORKER_TOKEN`, 시작 명령 `python run_worker.py`(서비스 루트 `worker`). CPU만 쓰며 가장 긴 경기(약 30분)도 평가 1.5~2초, 최대 메모리 약 77 MB로 쟀다(Windows).
   - **함께 고친 문제**: 파이썬 3.12 이상에서는 `s2protocol`이 제거된 `imp` 모듈을 불러오다 실패해, **기존 분석 워커(밴픽 복원)도 Railway 기본 파이썬에서는 전부 REJECTED/CORRUPT가 되었을 것**이다. `worker/bpm_replay/compat.py`가 호환 처리를 하며 3.13 깨끗한 환경에서 워커 테스트 40개와 종단 시험 28개가 통과했다.
   - 검증: `scripts/dev/eval-flow-test.mjs`(28항목: 큐 규칙, 실제 워커·실제 리플레이, 페이지 응답, 비공개·철회), `lib/replay/evaluation.test.ts`(6), `worker/tests/test_eval.py`(12). **미확인**: Linux에서의 실행(Windows에서만 돌려 봄), 실제 Railway 환경, 모바일 실기기.
   - **남은 일**: 사람끼리의 BPM 경기가 쌓이면 재검증·보정 후 퍼센트로 전환(`validated`를 true로), 모델이 바뀌면 `EVAL_VERSION`을 올리고 이전 평가를 다시 돌리는 절차(지금은 분석을 다시 돌려야 평가도 다시 한다).
6. **결과 저장**: `analysis`(버전 태그 포함, DB)와 `timeline`(스토리지, 본인 전용).

### 5.2 밴픽 복원 가능성 — 가장 큰 기술 리스크 → **프로토타입으로 해소 (2026-10-27)**

> **결과**: 모드를 고치지 않고 복원된다. 모드가 드래프트 적용 때 플레이어에게 숨은 업그레이드 `BPM_Ban_<유닛>`, `BPM_Pick_<유닛>`을 부여하고, 이것이 리플레이 트래커 스트림(`SUpgradeEvent`)에 남는다. 사용자 PC 리플레이 1,223개 중 BPM 게임 110개(사람이 직접 둔 게임 포함)를 오류 없이 복원했고, 봇 경기는 하네스의 자체 기록과 일치했다. 구현과 한계는 [`worker/README.md`](../worker/README.md), 코드는 `worker/bpm_replay/draft_decode.py`.
>
> **복원되는 것**: 플레이어별 최종 밴(상대가 건 것), 확장 유닛 픽과 그것이 대체한 기본 유닛. 밴픽 비율·승률 통계와 Replay Analysis의 밴픽 표에 충분하다.
> **복원되지 않는 것**: 밴 순서·패스·시각, 기본 유닛을 그대로 고른 선택(흔적 없음), **로비 설정(밴 수, Snake/Standard)과 모드 버전**. BPM 여부는 위 업그레이드의 유무로만 판정한다.
> **그래서 Challenge S1의 "Snake, 3 Bans" 자동 검증은 지금 불가능하다.** 실제 밴 개수로 3밴을 *추정*할 수 있을 뿐 Snake/Standard는 구분되지 않는다. 모드 v2.0에 설정 표식 업그레이드를 하나 더 부여하는 작은 수정(예: `BPM_Cfg_Ban3_Snake`)이 있으면 해결되며, 출시 전인 지금이 가장 싼 시점이다 → 모드 쪽 결정 필요. 표식의 성격(숨은 기술 트리 업그레이드이며 게임 상태와 리플레이에 남음)과 구현 규모는 [`Replay_Viewer_Plan.md`](./Replay_Viewer_Plan.md) §12.1.

아래 표는 프로토타입 전 후보 비교이며, 실제 채택된 경로는 표에 없던 "기존 업그레이드 기록"이다.

### (참고) 후보 경로 비교
밴픽은 맵 내부 Galaxy 대화상자로 진행된다. 기존 문서(`AI Open Source Analysis.md`)에는 s2protocol이 사람의 Dialog control 이벤트를 `replay.game.events`에 남길 **가능성**이 있으나, control ID의 의미는 자동으로 복원되지 않고, 임의 Galaxy 변수는 리플레이에 남지 않는다고 적혀 있다. 즉 **실제 리플레이에서 밴픽을 신뢰도 있게 복원할 수 있는지가 아직 확인되지 않았다.**

복원 경로 후보와 판단 순서:

| 경로 | 설명 | 장단점 |
|---|---|---|
| A. 인게임 결과 요약 | 밴픽 후 결과 창/채팅 메시지에 요약을 남김 | 리플레이 message 스트림으로 읽을 수 있으면 가장 쉬움. 모드 수정 필요 |
| B. 로스터 역추론 | 실제 생성된 유닛·건물에서 "무엇이 사용 가능했는지" 추정 | 모드 수정 불필요, 밴된 유닛은 직접 알 수 없음 |
| C. Dialog 이벤트 복원 | 클릭 이벤트 + 맵별 control ID 테이블 | 버전 종속, 취약 |
| D. 리플레이에 남는 흔적 삽입 | 모드가 밴픽 완료 시 리플레이 스트림에 남는 이벤트(예: 정해진 형식의 메시지나 트리거로 만든 관측 가능한 이벤트)를 발생시킴 | 모드 수정 필요, 가장 견고, 가능 여부는 프로토타입 |

권장: **Phase 0에서 프로토타입으로 A/D의 가능 여부를 먼저 확인**한다. 모드가 v2.0 출시 전이라 지금이 모드 쪽에 흔적을 심을 마지막으로 싼 시점이다. 어느 경로도 안 되면 밴픽 비율 통계는 약속한 대로 제공하기 어렵다(쟁점 6, 사용자 확인 필요). 콜로세움은 AI가 밴픽 결정을 직접 기록하므로(AI 텔레메트리) 이 문제와 무관하게 밴픽 데이터를 가진다.

### 5.3 분석 버전 관리
분석 결과에 `{analyzer_version, ai_model_version, mod_version, balance_version}`을 붙인다. 모델·밸런스가 바뀌면 재분석 잡을 만들 수 있게 `analysis`를 리플레이당 여러 버전으로 보관하고 최신만 노출한다. 설명 가능성을 위해 점수에 근거 이벤트 목록을 같이 저장한다.

### 5.4 분석 환경
`bpm-ai-engine`은 비공개 저장소이고 GPU가 필요하다. 워커는 **풀(pull) 방식**: 분석 머신이 큐를 폴링해 가져가고 결과를 서버에 쓴다. 서버가 분석 머신에 직접 접속하지 않는다. 워커가 내려가면 큐가 쌓이고 사용자에게는 "대기 중"이 보인다.

## 7. 통계 시스템

### 7.1 제공 항목 (패치노트 기준)
- 플레이어 밴픽 비율: 매치업, 밴 방식(Snake 등)·밴 수, 유닛별 pick 비율/ban 비율/승률 — **C2 동의 데이터만**.
- AI 밴픽/승률: 모델 버전별, 같은 축으로 나란히 표시.

### 7.2 신뢰도와 프라이버시 규칙 [제안]
- 표본이 최소 N판(예: 30) 미만인 셀은 수치 대신 "표본 부족"으로 표시한다(`BPM_Platform_Plan.md` §8.4의 "임의 수치로 채우지 않는다" 원칙 유지).
- 승률에는 신뢰 구간을 같이 표시한다.
- 소수 사용자가 통계를 좌우하지 않도록, 한 사용자의 기여를 기간당 상한으로 제한하거나 사용자 수 최소 기준(예: 서로 다른 10명 이상)을 둔다. 이는 개인 식별 방지이자 특정인의 통계 조작 방지다.
- 집계는 `game` 단위 중복 제거(§4.3).
- 밸런스 버전이 바뀌면 통계 기간을 분리한다. 구버전 데이터를 섞어 현재 밸런스 판단에 쓰지 않는다.

### 7.3 갱신
- 업로드 분석 완료 시 증분 갱신, 매일 전체 재계산으로 보정. "실시간 AI 밴픽 비율"은 분 단위 지연을 허용하는 것으로 정의한다.

- 같은 경기 지문 중복, 비정상적으로 짧은 경기, 치트/맵 수정 흔적을 거른다.
- 지나치게 빠른 클리어나 의심 리플레이는 **운영자 수동 검수 큐**로 보내고, 상금 확정은 사람 승인 후에만 한다.

- 사용자 PC에서 변조된 모드로 경기한 경우를 완전히 막을 수는 없다. 한계로 인정하고, 상금 대상자는 최종 단계에서 리플레이 원본 검수와 필요 시 재경기 확인을 한다.

### 8.3 이벤트용 동의
이벤트 집계에는 사용자 닉네임이 순위표에 공개될 수 있다. C1/C2와 별도로 **"이벤트 참가·순위표 공개" 동의**(E1)를 둔다. 상금 수령자는 오프라인으로 연락을 받는다.

### 8.4 AI Analysis Score [사용자 정의 필요]
패치노트는 "AI Analysis Score 상금(20, 10, 5)"이라고만 했다. 산식 후보: 밴픽 품질 점수 + 운영 효율 + 교전 판단. 상금이 걸리므로 **산식과 동점 처리, 재현성(같은 리플레이는 항상 같은 점수)** 을 이벤트 공지 전에 확정해야 한다. 분석 모델 버전이 바뀌면 점수가 바뀌므로 **이벤트 기간 동안 평가 모델 버전을 고정**한다.

## 10. 운영·보안

- **스토리지 비공개**: 버킷 공개 쓰기 금지, 읽기는 짧은 수명의 서명 URL.
- **파서 격리**: 업로드 파일은 신뢰하지 않는다. 파서는 샌드박스 프로세스, 타임아웃, 메모리 상한. 악성 MPQ 대비.
- **접근 통제**: 원본 리플레이 읽기는 본인·운영자·(콜로세움 공개분)만. 학습 파이프라인은 `v_training_eligible` 뷰만.
- **로깅**: 개인정보(핸들, IP)는 보존 기간을 두고 파기. 감사 로그는 별도 보존.
- **백업**: DB 일일 백업, 스토리지 버전 관리. 삭제 요청은 백업까지 반영하는 만료 기한을 약관에 명시.
- **모니터링**: 큐 길이, 분석 시간 p50/p90, 실패율(코드별), 업로드 거부 비율, 워커 생존 신호.
- **비용 가늠** (측정 전 가정): 리플레이 약 0.2~1MB/판 가정 시 1만 판에 수 GB 수준. 스토리지는 문제 없고 병목은 GPU 분석 처리량이다. `bpm-ai-engine`의 병렬 러너 처리량 실측(동시 3, 시간당 99판)은 게임 시뮬레이션 기준이며 분석 처리량과는 다르므로 분석 시간을 별도로 측정해야 한다.

**Phase 0 구현 상태 (2026-10-27)**: 운영자 업로드 API, 공개 목록·상세·순위, AI 리플레이 다운로드, 예약 공개를 구현하고 합성 데이터로 검증했다([Colosseum_Ingest.md](./Colosseum_Ingest.md)). Phase 0이 별도 마일스톤인 이유: 이벤트가 닷새 뒤이고 거기에 필요한 건 인증된 사용자 기능이 아니다. 또 Phase 0의 `game`/`replay`/`analysis` 테이블과 분석 파이프라인은 Phase 1에서 그대로 쓴다. 호스팅 결정(쟁점 4)은 Phase 0 시작 전에 필요하다.

**Phase 1의 선행 조건**: 약관·개인정보 처리방침, 로그인 제공자 결정, 밴픽 복원 방식 확정(필요하면 모드 v2.0 수정).

**Phase 1 구현 상태 (2026-10-27, 업로드 시스템)**: 런처(`uploader/`, [README](../uploader/README.md))와 서버 업로드 경로를 만들고 종단 시험까지 했다. 내용과 §4와의 차이:
- 런처: 폴더 감시 → 다 써질 때까지 대기 → **로컬에서 BPM 판별(아니면 전송 안 함)** → SHA-256 → 업로드, 재시도·재시작 복구, 트레이 UI. 사용자 리플레이 1,220개에서 서버 디코더와 같은 110개를 BPM으로 판정.
- 서버: 기기 코드 로그인(RFC 8628 방식), 동의 C1~C3(+변경 이력, 기존 리플레이에 즉시 반영), `POST /api/uploads`(해시 검증·사용자별 중복 제거·일일 한도 200·C1 필요), `GET /api/uploads/{id}`, `GET /api/me/*`, `/device` 승인 페이지. API 27개 점검 스크립트 `scripts/dev/upload-flow-test.mjs`.
- §4.2와 다른 점: **사전 서명 URL 대신 서버로 직접 업로드**(리플레이 ≤10MB라 단순한 쪽을 택함, 트래픽이 커지면 R2 서명 URL로 전환), 경기 지문(§4.3)은 업로드 시점이 아니라 읽을 때 계산하고(§4.3 구현 항목), 업로드는 사용자별 해시 중복만 처리.
- 업로드된 리플레이는 `QUEUED`로 쌓이고, 분석 워커가 가져가 처리한다(아래).

**분석 워커 구현 상태 (2026-10-27)**: 서버의 작업 대기열(`/api/worker/*`, 전용 `WORKER_TOKEN`)과 Python 워커(`worker/run_worker.py`, [README](../worker/README.md))를 만들고 실제 리플레이로 종단 시험했다.
- 상태 흐름 `QUEUED → ANALYZING → READY | REJECTED(NOT_BPM/CORRUPT/UNSUPPORTED) | FAILED`. 한 작업은 한 워커에게만 배정(10분 임대, 만료 시 재배정), 실패는 2분·4분 백오프로 재시도 후 3번째에서 확정. 임대가 끝난 워커의 늦은 결과는 409로 거부.

## 12. 완료 기준

- **Phase 0**: 콜로세움 리플레이 전량이 예약 시각에 공개되고, 목록에서 매치업·라운드·밴픽·승패로 필터할 수 있으며, 다운로드가 동작한다.
- **Phase 1**: 업로드 → 분석 완료까지 p90 목표 시간 내. C2/C3 끄면 공개 조회·집계·학습 뷰에서 즉시 사라지는 것을 자동 테스트로 확인. 철회·삭제 요청이 동작.
- **Phase 2**: 표본 부족 셀이 임의 수치로 채워지지 않고, 사용자 수 최소 기준이 적용된다.
- **Phase 3**: 규칙 표의 모든 판정이 사유 코드와 함께 재현되며, 의심 사례가 자동 확정되지 않는다.
- 공통: 동의 필터 테스트(공개 API, 집계, 학습 뷰 3경로)가 CI에서 항상 통과.
