## 1. 현재 상태 진단

### 1.1 색상이 서로 다른 의미로 충돌한다
`globals.css`는 종족색을 `--terran-accent`(sky/cyan), `--protoss-accent`(amber), `--zerg-accent`(purple)로 고정 정의했지만, 실제 화면에서는 같은 색이 종족과 무관하게 재사용된다.
- 홈의 밴픽 3단계 카드: STEP01=sky, STEP02=amber, STEP03=emerald (종족과 무관, 순서 색)
- 홈/대회 페이지의 룰셋 3종: Standard=emerald, No Repeat=sky, Snake=amber (역시 종족과 무관)
- 대회 페이지 상단 탭: 룰셋=sky, 리플레이=emerald, 관전=rose (또 다른 의미)
- 위키 상세: Terran=sky, Protoss=amber, Zerg=purple (여기서만 종족색 의미로 사용)

결과적으로 사용자는 "이 파란색이 테란을 뜻하는지, 선택된 탭을 뜻하는지, 1번 스텝을 뜻하는지"를 화면마다 다시 학습해야 한다. 색이 정보를 줄여야 하는데 오히려 해석 부담을 늘린다.

### 1.2 타이포그래피 위계가 두 단계뿐이다
헤더(`text-3xl`~`text-6xl`, font-black)와 본문(`text-xs`, `text-[10px]`, `text-[11px]`)만 존재하고 중간 크기가 거의 없다. 카드 제목, 설명문, 배지 라벨, 통계 수치가 대부분 11~12px 안에서 폰트 굵기로만 구분되어, 화면을 스캔할 때 눈이 쉴 지점이 없다. `LinearWikiView`만 예외적으로 15~17px를 쓰는데, 이 때문에 위키 안에서 탭을 바꾸면 글자 크기가 크게 널뛴다.

### 1.3 카드 컴포넌트가 매번 새로 스타일링된다
`bpm-glass rounded-2xl border-slate-800 p-6` 패턴이 홈, 위키, 패치, 대회, AI 등 거의 모든 섹션에서 반복되지만 공유 컴포넌트가 없다. 배지(`STEP 01`, `PRESET 1`, `LIVE`, `OFFICIAL`)도 페이지마다 색과 padding이 조금씩 다르게 인라인으로 작성되어 있다. 공통 `Card`, `Badge`, `SectionHeader` 컴포넌트가 없어서 통일감이 없고, 향후 수정 시 한 곳을 고쳐도 다른 페이지는 그대로 남는다.

### 1.4 컨테이너 너비가 페이지마다 다르다
대부분 `max-w-7xl`이지만 유닛 상세(`/wiki/units/[id]`)는 `max-w-6xl`이고, 위키 홈의 "전체 위키" 탭 내부(`LinearWikiView`)는 그 안에서 다시 `max-w-3xl`로 좁아진다. 같은 `/wiki` 페이지에서 탭만 바꿔도(전체 위키 ↔ PTR ↔ 확장 유닛) 콘텐츠 폭이 3xl → 자유 → 7xl 그리드로 요동쳐 레이아웃이 튄다.

### 1.5 홈페이지와 대회 페이지의 정보가 중복된다
홈의 "지원 룰셋 프리셋" 섹션(3개 카드: Standard/No Repeat/Snake)과 `/tournaments`의 "룰셋별 밴픽 체험" 탭이 거의 동일한 카드 3개를 다시 보여준다. 첫 방문자가 홈에서 이미 본 내용을 대회 페이지에서 그대로 다시 읽어야 하며, 홈페이지 자체도 Hero → 3단계 워크플로우 → 룰셋 3종 → 맵/HUD 탭 → 4단계 실행 가이드까지 대형 카드 그리드 섹션이 5개 연속으로 이어져 스크롤 피로가 크다.

### 1.6 위키의 세 탭이 서로 다른 UI 패턴과 데이터 범위를 섞어 쓴다
`/wiki`는 "현재 공식 버전 전체 위키"(줄글 리스트, `allLiveUnits`), "PTR 예정 사항"(별도 리스트), "확장 유닛 도감 17종"(카드 그리드, `bpmUnits`)를 탭으로 전환한다. 그런데 첫 번째 탭은 전체 유닛을 다루는 롱폼 문서이고 세 번째 탭은 그 안의 부분집합(17종 확장 유닛)을 카드로 다시 보여주는 것이라, 사용자가 "확장 유닛은 전체 위키에도 들어있는지, 별도인지"를 탭 이름만으로 알 수 없다. 또한 첫 번째 탭은 상단에 종족 구분만 있고 유닛이 많아지면 점프 링크나 목차 없이 위에서 아래로 계속 스크롤해야 한다.

### 1.7 데모/목업 데이터가 실제 데이터처럼 보인다
`BPM_Platform_Plan.md` 13절은 "실제 데이터가 없는 항목은 Coming Soon 또는 Not enough data로 표시한다"를 원칙으로 명시하지만, 실제 화면(`/tournaments`의 리플레이 분석 결과, 관전 카드의 Maru vs herO 스코어, `/matches/demo/live`)은 하드코딩된 가짜 결과를 실데이터와 동일한 스타일로 보여준다. "DEMO"라는 라우트 경로(`/matches/demo/live`)를 통해서만 알 수 있고 화면 안에는 데모임을 알리는 표시가 없어, 방문자가 실제 대회 데이터로 오인할 수 있다.

### 1.8 그리드 컬럼 수가 섹션마다 바뀐다
홈 안에서만도 3열(밴픽 단계) → 3열(룰셋) → 3열/2열(맵·HUD 탭 전환) → 4열(실행 가이드)로 컬럼 수가 계속 바뀐다. 각 그리드가 독립적으로 결정되어 있어 수직 리듬이 없고, 페이지를 내려갈수록 레이아웃이 예측 불가능하게 느껴진다.

## 2. 개선 방향 (우선순위 순)

### Phase 1 — 디자인 토큰 정리 (기반 작업, 가장 먼저)
1. **색상 역할 재정의**: 종족색(sky/amber/purple)은 유닛·종족 표시에만 사용하도록 고정한다. 상태/의미색은 별도 팔레트로 분리한다 — 예: `선택됨`은 sky 고정, `밴/위험`은 rose 고정, `완료/활성`은 emerald 고정, `주의/타이머`는 amber 고정. 종족 표시가 없는 화면(대회 탭, 룰셋 카드, 스텝 번호)에서는 종족색을 절대 재사용하지 않는다.
2. **타이포그래피 스케일 추가**: 현재 `text-3xl`(제목)과 `text-xs`(본문) 사이에 `text-sm`/`text-base` 단계를 표준으로 넣어 카드 제목·본문·캡션 3단 위계를 만든다. `LinearWikiView`의 15~17px 본문 크기를 다른 위키 탭과 맞춘다.
3. **공유 컴포넌트 추출**: `components/ui/Card.tsx`, `Badge.tsx`, `SectionHeading.tsx`를 만들어 지금 인라인으로 반복되는 `bpm-glass rounded-2xl p-6 border-slate-800`와 배지 스타일을 교체한다. 이후 색/여백 조정은 한 파일만 고치면 전체 사이트에 반영된다.
4. **컨테이너 폭 통일**: 모든 페이지 본문을 `max-w-7xl`로 통일하고, `LinearWikiView`의 `max-w-3xl` 제한을 제거하거나 최소 `max-w-4xl` 이상으로 넓혀 탭 전환 시 폭이 튀지 않게 한다.

### Phase 2 — 페이지별 정보구조 정리
5. **홈페이지 축소**: 룰셋 3종 카드 섹션을 홈에서 제거(또는 카드 3개 → 한 줄 요약 배너로 축소)하고 "자세히 보기 → /tournaments" 링크로 대체한다. 홈은 Hero + 밴픽 3단계 + How to Play + 최신 패치 미리보기 정도로 스크롤 길이를 줄인다.
6. **위키 탭 재구성**: "전체 위키"와 "확장 유닛 도감"의 관계를 명시한다(예: 확장 유닛 탭 상단에 "이 17종은 전체 위키에도 포함되어 있으며, 여기서는 카드 형태로 빠르게 훑어볼 수 있습니다" 안내, 또는 확장 유닛을 전체 위키 리스트 안에서 필터 옵션으로만 제공하고 별도 탭은 없앤다). "전체 위키" 리스트 상단에 종족별 유닛 이름 목차(점프 링크)를 추가한다.
7. **데모 데이터 라벨링**: `/tournaments`의 리플레이 분석 결과 카드와 관전 카드, `/matches/demo/live` 전체에 "DEMO DATA" 배지를 눈에 보이게 부착해 실제 대회 데이터와 시각적으로 구분한다.

### Phase 3 — 시각 리듬 다듬기
8. **그리드 컬럼 수 표준화**: 카드 그리드는 3열을 기본값으로 통일하고(모바일 1열 → 태블릿 2열 → 데스크톱 3열), 4열이 필요한 경우(How to Play)는 예외로 남기되 인접 섹션과 최소 한 번은 시각적 구분선(배경 톤 변화)을 유지한다.
9. **배지/카드 톤 다운**: 모든 카드에 색 테두리+글로우를 기본 적용하는 대신, 강조가 필요한 카드(선택됨, LIVE, 최신)에만 색을 쓰고 나머지는 중립 톤(slate)으로 낮춰 정말 중요한 요소가 눈에 띄게 한다.

## 4. 진행 방식

1. Phase 1(토큰/공유 컴포넌트)을 가장 먼저 끝내야 이후 페이지별 수정이 반복 작업 없이 적용된다.
2. 각 Phase는 별도 작업 단위로 진행하며, 완료 후 `npm run lint && npm run build`로 회귀를 확인한다.
3. 기능/데이터 모델 변경은 포함하지 않으며, 이번 개선은 시각 레이어(className, 공유 컴포넌트, 카피)에 한정한다.
